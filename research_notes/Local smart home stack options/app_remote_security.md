## 1. App technology: PWA served by the hub vs Capacitor vs Flutter vs React Native/Expo vs Kotlin/Compose Multiplatform vs native — and what a PWA can really do on iOS/iPadOS and Android in late 2026

### Takeaway
A hub-served PWA is the only option that needs no store, no code signing and no developer account on either platform, and in late 2026 it covers the control UI, push-to-talk microphone capture (HTTPS required), Web Push (on iOS only after "Add to Home Screen", and always relayed through the browser vendor's push servers) and screen wake lock. It falls short exactly where a smart-home app wants background behaviour: no background sync or persistent socket on iOS, WebSockets that die or hang after backgrounding, no always-listening voice, no Web Bluetooth on iOS, and no truly cloud-free notifications — those need a native shell, which re-introduces the signing/distribution problem covered in question 2.

### Cited Findings

**iOS / iPadOS Home Screen web apps (PWA)**
- Install flow: since iOS/iPadOS 26 (Sept 2025) every site added to the Home Screen opens as a web app by default; the user can switch off "Open as Web App" in the Add-to-Home-Screen sheet. Before iOS 26 this required a manifest or meta tag. — [WebKit, Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/) [snippet]
- There is no install-prompt API on iOS (`beforeinstallprompt` is Chromium-only); installation is the manual Share → Add to Home Screen step. Third-party iOS browsers can offer Add to Home Screen since 16.4. — [OpenPWA survey, Oct 2026](https://openpwa.net/news/pwas-on-iphone-what-works-and-what-does-not-october-2026/) [S]; [WebKit blog](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) [P]
- Web Push: available since iOS/iPadOS 16.4, only for web apps added to the Home Screen; permission must be requested from a direct user gesture; "You do not need to be a member of the Apple Developer Program to use it." — [WebKit blog](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) [P]; [Apple docs](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) [P]
- No silent push: "Safari doesn't support invisible push notifications. Present push notifications to the user immediately after your service worker receives them. If you don't, Safari revokes the push notification permission for your site." So push cannot be used to wake the PWA to refresh state in the background. — [Apple docs](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) [P]
- Per a reading of WebKit source (not a documented guarantee): the service worker gets ~30 s to call `showNotification()`, and the third silent push removes the origin's subscription; iOS does not fire `pushsubscriptionchange`, so apps should re-subscribe on every launch. Apple returns HTTP 201 even if the device later drops the message. — [progressivewebapps.com iOS web push guide (written after 14 Sep 2026)](https://progressivewebapps.com/background/ios-web-push/) [S]
- Declarative Web Push (notification shown without running a service worker) shipped in Safari 18.4 for iOS/iPadOS 18.4 on 31 Mar 2025. The same release "Fixed Wake Lock API for Home Screen Web Apps", "Added WebM support to MediaRecorder", added Ogg Opus, and "Fixed voice search to not re-prompt for camera or microphone permission after a page-initiated same origin navigation". — [Safari 18.4 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-18_4-release-notes) [P]
- iOS web-push notifications ignore `image`, `badge`, `actions`, `requireInteraction`, `renotify`, `vibrate`, `timestamp`; `tag` does not reliably replace. — [progressivewebapps.com](https://progressivewebapps.com/background/ios-web-push/) [S]
- Safari 27.0 (released 14 Sep 2026): no push-specific changes in the release notes and nothing new for Home Screen web apps according to two secondary guides; WebKit's own feature list highlights other items (customizable select, JSPI, service-worker static routing API, etc.). — [progressivewebapps.com](https://progressivewebapps.com/background/ios-web-push/) [S]; [MobiLoud guide](https://www.mobiloud.com/blog/progressive-web-apps-ios/) [snippet]; [WebKit Features for Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/) [snippet]
- Background work: Background Sync, Periodic Background Sync and Background Fetch are unsupported on iOS; "queued work completes only while the app is open". caniuse data (read 25 Nov 2026) lists Background Sync as "n" for iOS Safari 27.2 and "y" for Chrome for Android 157. — [OpenPWA](https://openpwa.net/news/pwas-on-iphone-what-works-and-what-does-not-october-2026/) [S]; [caniuse data file](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/background-sync.json) [P]
- Web Bluetooth: caniuse data (read 25 Nov 2026) — iOS Safari 27.2 "n" ("Safari on iOS and iPadOS has no native support"), desktop Safari "n", Firefox "n", Chrome for Android 157 "y" (support "varies by OS"), Samsung Internet "y". Web NFC and WebUSB are also listed as unsupported on iOS. — [caniuse data file](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/web-bluetooth.json) [P]; [OpenPWA](https://openpwa.net/news/pwas-on-iphone-what-works-and-what-does-not-october-2026/) [S]
- Microphone: `getUserMedia()` "can only be used in secure contexts; in insecure contexts, `navigator.mediaDevices` is `undefined`"; browsers must ask at least the first time and how long a grant persists is browser-specific. — [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) [P]
- Microphone in standalone mode has a history of iOS-specific bugs: recurring permission prompts when the URL hash changed (WebKit bug 215884; a commenter noted iOS 14.5 stopped per-page prompts but permission still was not kept across sessions), and a 2024 comment that the microphone "stopped working" in Add-to-Home-Screen apps while Safari worked. No 2025–2026 source was found that confirms current behaviour. — [WebKit bug 215884](https://bugs.webkit.org/show_bug.cgi?id=215884) [snippet]
- WebSocket lifetime: no documented background lifetime exists. Bug reports: WebKit bug (Feb 2026, Safari/iOS 26.3) — after ≥10 s in the background, `new WebSocket()` to a local `ws://` hangs in CONNECTING while HTTP still works, in both Safari tabs and Home Screen mode; another report of WebSocket handshakes failing in Safari and standalone mode on iOS 26 while Chrome/Firefox on the same device work. — [WebKit bug 308073](https://bugs.webkit.org/show_bug.cgi?id=308073) [snippet]; [WebKit bug 298616](https://bugs.webkit.org/show_bug.cgi?id=298616) [snippet]
- iPadOS 26 regression specific to LAN PWAs: an installed PWA using `http://`/`ws://` on a local network had its WebSocket closed by the iPad about one second after connecting (iPadOS 26.2; not seen on iPadOS 18 or in Chrome on the same device). Apple DTS confirmed bug FB21416603 was assigned to WebKit and still open in Jan 2026; the only reported workaround was setting the Wi-Fi HTTP proxy to "Auto". `wss://` was not tested in the thread. — [Apple Developer Forums thread 811063](https://developer.apple.com/forums/thread/811063) [P]
- Local-network permission: iOS "local network privacy" prompts apply to third-party apps' own networking, but "Traffic originating from WKWebView, SFSafariViewController, and Safari doesn't require local network access." Native code that resolves `.local` names or uses Bonjour does need the permission (and `NSLocalNetworkUsageDescription`). Technote revised 6 Oct 2026. — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) [P]
- Storage: origin quota up to ~60% of disk since Safari 17; the 7-day cap on script-writable storage applies to Safari browsing, while Home Screen web apps have their own counter based on actual app use (secondary survey; applicability "unverified"). An installed web app has storage separate from Safari, so the user must sign in again after installing. — [OpenPWA](https://openpwa.net/news/pwas-on-iphone-what-works-and-what-does-not-october-2026/) [S]
- EU status: Apple reversed its iOS 17.4-beta removal of Home Screen web apps before release (March 2024); they remain supported in the EU. — [progressivewebapps.com](https://progressivewebapps.com/background/ios-web-push/) [S]; contradicted by [MagicBell guide, updated 20 Mar 2026](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide) [S], which still says push/standalone are removed in the EU and cites no primary source — treat the MagicBell claim as outdated.

**Android (Chrome) PWAs**
- Installing a PWA from Chrome creates a WebAPK: "Chrome requests a specialized server (WebAPK minting server) to generate a real Android APK for the web app", which is then installed "via Play Store or download". — [Chromium docs](https://chromium.googlesource.com/chromium/src/+/main/components/webapps/docs/android_architecture.md) [P]; [web.dev WebAPKs](https://web.dev/articles/webapks) [P]
- Open Web Advocacy states WebAPK minting goes through a Play Services API restricted to Chrome (Samsung devices excepted), i.e. other browsers cannot mint WebAPKs. — [Open Web Advocacy](https://open-web-advocacy.org/blog/google-must-share-the-ability-to-install-web-apps-in-android/) [snippet]
- Web Push on Android: the push service is chosen by the browser and the developer has no control over it; the payload must be encrypted so the push service cannot read it, while TTL, urgency and topic are delivery instructions the service sees. ntfy's docs give "fcm.googleapis.com" as the typical browser-provided endpoint. — [web.dev, How push works](https://web.dev/articles/push-notifications-how-push-works) [P]; [ntfy config docs](https://docs.ntfy.sh/config/) [P]
- Web Bluetooth and Background Sync are supported in Chrome for Android 157 per caniuse data (read 25 Nov 2026). — [caniuse web-bluetooth](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/web-bluetooth.json) [P]; [caniuse background-sync](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/background-sync.json) [P]

**Wrappers and native frameworks**
- Capacitor is "a cross-platform native runtime" for running web apps natively on iOS and Android; the docs show v8 as current and v9 as "next" (Nov 2026). — [Capacitor docs](https://capacitorjs.com/docs) [P]
- React Native/Expo can be built entirely on local tooling: `npx expo run:ios` / `run:android` compile "using your locally installed Android SDK or Xcode"; no EAS cloud service is needed (Xcode / Android Studio are prerequisites). — [Expo docs, local app development](https://docs.expo.dev/guides/local-app-development/) [P]
- Compose Multiplatform for iOS has been declared stable and production-ready since 1.8.0 (May 2025); 1.11.0 followed in May 2026. — [JetBrains blog](https://blog.jetbrains.com/kotlin/2025/05/compose-multiplatform-1-8-0-released-compose-multiplatform-for-ios-is-stable-and-production-ready/) [snippet]
- Current-version claims from an aggregator comparison (unverified): Flutter 3.47 (12 Aug 2026), React Native 0.88 (19 Oct 2026), Compose Multiplatform 1.12.2 (Oct 2026). — [tech-insider comparison](https://tech-insider.org/react-native-vs-flutter-2026/) [snippet]
- What a free Apple "Personal Team" build can use (matters for any wrapper/native iOS app): remote push notifications, Sign in with Apple, iCloud, NFC and associated domains require the paid programme; App Groups, Background Modes, HomeKit, Keychain Sharing and **local** notifications work on a free account. — [Expo blog, 2 Nov 2026](https://expo.dev/blog/apple-developer-program-explained-free-vs-paid.md) [S]
- Android wrappers/native apps talking to a LAN hub: apps targeting API 24+ trust only system CAs by default (user-installed CAs are ignored unless a network-security-config opts in or bundles the CA), and cleartext HTTP is disabled by default from API 28. — [Android network security configuration](https://developer.android.com/privacy-and-security/security-config) [P]

### Inferences
- Summary by option (derived from the findings above):

| Option | What works | What does not | Hidden dependency / cost |
|---|---|---|---|
| PWA served by the hub | One codebase; no store, signing or account; control UI, mic push-to-talk, wake lock; Web Push | iOS: no background execution, WebSocket only while foreground, no Bluetooth, mic-permission behaviour uncertain; no always-listening anywhere | HTTPS certificate the phones trust (question 4); Web Push goes via Apple/Google/Mozilla servers; Android install uses Google's WebAPK minting server |
| Capacitor around the same web code | Same UI plus native plugins; on Android a foreground service, bundled private CA, no WebAPK server | On iOS gains little without paid entitlements (no APNs on a free team) | iOS signing limits (7-day profiles) or 99 USD/yr; Android sideload rules |
| Flutter / React Native / Compose Multiplatform | Native UI, all native APIs, local builds possible | Rewrites the UI instead of reusing the hub's web UI; same iOS signing limits | Same as Capacitor, plus a second UI codebase |
| Fully native (Swift + Kotlin) | Everything the OS allows (Android foreground services, iOS Local Push Connectivity if entitled) | Two codebases | Same distribution limits; highest effort |

- For a single-household app the framework choice matters far less than the distribution constraint: every non-PWA route on iOS hits free-provisioning limits, so "PWA everywhere, plus an optional small Android shell for background features" is the lowest-dependency design.
- Because WKWebView traffic is exempt from the iOS local-network prompt, a Capacitor shell loading the hub's pages should not show that prompt for web content; native plugins doing their own networking or mDNS discovery would.
- The iPadOS 26 `ws://` bug and the secure-context rules both point the same way: serve the hub over `https://`/`wss://` from day one and implement aggressive WebSocket reconnect with an HTTP fallback on iOS.

### Gaps
- No 2025–2026 primary source on whether microphone permission persists across launches of an iOS Home Screen web app; needs a device test on iOS 26/27.
- No documented background lifetime for WebSockets in iOS Home Screen web apps — only bug reports; whether FB21416603 is fixed in current iPadOS was not confirmed.
- Whether Chrome can mint a WebAPK for a LAN-only origin with a private-CA certificate, and what the fallback is, was not found.
- WebKit's Safari 27 post was seen only as a search snippet; "nothing new for Home Screen web apps in iOS 27" rests on secondary sources.
- Framework version numbers come from one aggregator; Tauri mobile was not researched.

## 2. Distribution: iOS without paying for the Apple Developer Program, and Android sideloading under Google's developer-verification programme

### Takeaway
iOS (Nov 2026): a personal native app can be run for free only with 7-day "Personal Team" signing (max 3 apps per device, no push-class capabilities), which SideStore/AltStore merely automate; TestFlight, year-long profiles and APNs need the 99 USD/yr programme, and EU/Japan/Brazil alternative distribution is aimed at organisations and still needs membership plus notarization. Android: installing your own APK remains possible — ADB installs are explicitly untouched, a free no-ID "limited distribution" account covers up to 50 devices, and an "advanced flow" re-enables unverified installs after a one-time 24-hour wait; enforcement so far (since 30 Sept 2026) covers only participating stores in four countries, with a global, all-sources rollout starting January 2027.

### Cited Findings

**iOS — free provisioning**
- With a free Apple Account, Xcode creates a "Personal Team" for on-device testing: up to 10 App IDs, up to 3 devices, up to 3 apps per device, and provisioning profiles that expire 7 days after issuance, after which you must "rebuild and reinstall your app to your device". (Limits as extracted from Apple's page; the table formatting was partly lost in extraction.) — [Apple, Choosing a Membership](https://developer.apple.com/support/compare-memberships/) [P]
- Independent confirmation (2 Nov 2026): free profiles lapse after 7 days and the app stops opening; 3 apps per iPhone; paid development profiles last up to a year; TestFlight and Ad Hoc distribution require the paid programme (99 USD/yr). — [Expo blog](https://expo.dev/blog/apple-developer-program-explained-free-vs-paid.md) [S]

**iOS — AltStore / SideStore**
- SideStore (reviewed 28 Jun 2026 on an iPhone 16 with iOS 26.5): signs with a regular Apple account, needs a computer and cable for the initial install (via the "iloader" tool), needs the LocalDevVPN app connected, and refreshes apps on-device before the 7-day expiry; limits are 3 active apps including SideStore itself and 10 app installs per week; requires iOS 15+. Unlike AltStore PAL it can install non-notarized apps. — [GIGAZINE](https://www.gigazine.net/gsc_news/en/20260628-sidestore-sideloading-ios) [S]
- AltStore Classic uses the same free signing and needs a Mac/PC reachable every 7 days to refresh. — [WhistleOut guide](https://www.whistleout.com/CellPhones/Guides/how-to-sideload-apps-on-ios-with-altstore-sideloadly) [snippet]

**iOS — EU alternative distribution and Web Distribution**
- New EU terms announced 18 Aug 2026, effective 1 Oct 2026: the per-install Core Technology Fee is replaced by a 5% Core Technology Commission on digital transactions for apps distributed outside the App Store; eligibility for marketplaces/web distribution is widened; "every alternatively distributed app" must still go through Notarization. — [Apple Newsroom](https://www.apple.com/newsroom/2026/08/apple-announces-changes-for-apps-in-the-european-union/) [P]
- Web Distribution requirements (page read Nov 2026): the Account Holder must accept the current Apple Developer Program License Agreement and request access; "your organization" must meet one of seven criteria (fee-waived nonprofit/education/government; Dun & Bradstreet low-risk score; stock-exchange listing; funding from a listed VC firm; 1,000,000 USD stand-by letter of credit; a clean financial audit within three years; or two years' good standing plus an app with over one million first annual installs). Apps must be notarized and can only be installed from a domain registered in App Store Connect; users need iOS 17.5+ / iPadOS 18+. — [Apple, Web Distribution in the EU](https://developer.apple.com/support/web-distribution-eu/) [P]
- Outside the EU: alternative marketplaces are available in Japan from iOS 26.2 and in Brazil from iOS 26.5 (29 countries in total); UK and Australia had not launched in the reports found. — [Apple MarketplaceKit docs](https://developer.apple.com/documentation/marketplacekit/participating-in-alternative-distribution-for-specific-regions) [snippet]; [heise](https://heise.de/-11070764) [snippet]; [MacRumors, 18 Jun 2026](https://macrumors.com/2026/06/18/apple-announces-ios-app-store-changes-in-brazil) [snippet]

**Android — developer verification status**
- Timeline per Google: verification opened to all developers 30 Mar 2026; Android Developer Verifier system service from April 2026; limited-distribution accounts and the "advanced flow" launched globally in August 2026; from 30 Sept 2026 protections apply "to participating stores in select regions" (Brazil, Indonesia, Singapore, Thailand) on certified devices. — [Android Developers Blog, 30 Mar 2026 (updated 29 Sep 2026)](https://developer.android.com/blog/posts/android-developer-verification-rolling-out-to-all-developers-on-play-console-and-android-developer-console) [P]
- 19 Nov 2026 update: protections "went live on September 30 for participating stores" in the four countries; "global rollout will begin in January 2027" with seven distributors (Google Play, Galaxy Store, Honor, Oppo, Xiaomi, Transsion, Vivo) and will "gradually expand to all countries to cover all installation sources on certified Android devices over several months". — [Android Developers Blog, 19 Nov 2026](https://developer.android.com/blog/posts/android-developer-verification-2027) [P]
- Direct sideloading is not yet affected: "If you distribute your app through other stores, or if users sideload your app directly, these new verification requirements won't apply to your app yet" (FAQ entry dated 15 Jul 2026). Scope: certified Android devices running Android 8 (API 26)+, delivered through Google Play services (entry dated 10 Nov 2026). — [Google developer-verification FAQ](https://developer.android.com/developer-verification/guides/faq) [P]; an earlier press report cited Android 7+ — [Android Authority, 1–2 Oct 2026](https://www.androidauthority.com/how-to-bypass-android-developer-verification-sideloading-rules-3718002/) [S]
- ADB: "As a developer, you are free to install apps without verification with ADB"; "there are no changes to how ADB works... The waiting period does not apply to ADB installs." — [FAQ](https://developer.android.com/developer-verification/guides/faq) [P]
- Hobbyist route: the limited distribution account is free, needs no government ID, and shares apps "with up to 50 devices that end-users have explicitly authorized" (raised from 20) through a QR-code/link handshake with on-device consent; it requires a Google Account with 2-Step verification, a Google payments profile (legal name and address) and a contact email. The full-distribution account costs 25 USD and requires identity verification. — [Limited distribution guide](https://developer.android.com/developer-verification/guides/limited-distribution) [P]; [Android Developers Blog, 19 Nov 2026](https://developer.android.com/blog/posts/android-developer-verification-2027) [P]; [FAQ](https://developer.android.com/developer-verification/guides/faq) [P]
- Advanced flow for users: enable developer options, confirm you are not being coached, restart, wait one day (one-time), re-authenticate, then allow unverified installs for 7 days or indefinitely; developer options need not stay on. Unregistered apps "can only be installed or updated when the advanced flow is enabled or by using ADB". Gradual rollout began 18 Aug 2026. — [FAQ](https://developer.android.com/developer-verification/guides/faq) [P]; [9to5Google](https://9to5google.com/2026/08/18/google-gradually-rolling-out-androids-advanced-sideloading-ahead-of-developer-verification/) [snippet]
- Press detail: previously installed sideloaded apps keep working but cannot be updated without one of these routes; Shizuku (wireless debugging) also works; custom ROMs such as LineageOS and GrapheneOS reportedly do not ship the verifier. — [Android Authority](https://www.androidauthority.com/how-to-bypass-android-developer-verification-sideloading-rules-3718002/) [S]

### Inferences
- iOS, realistic ranking for a personal app: (1) PWA — free and permanent; (2) Xcode Personal Team or SideStore — free but a weekly re-sign that depends on Apple's signing servers, an Apple account and internet, and lacks push-class entitlements; (3) paid programme — removes the friction but is a yearly fee, which conflicts with the "no subscription" constraint. EU Web Distribution is not a hobbyist path.
- Android, for the owner's own phones: `adb install` (or Android Studio "Run") has no account dependency at all and is unaffected by the programme; the limited-distribution account is the smoother path for family devices but ties the app to a Google account with a legal name and address on file.
- From 2027 a self-built APK copied to a certified phone and tapped will be blocked unless the package is registered, the phone has completed the advanced flow, or ADB is used. Old wall-panel devices on Android 7 or below, or without Google certification, fall outside the scheme.

### Gaps
- No month-by-month or country schedule for the 2027 global expansion beyond "begins January 2027 ... over several months".
- Whether the limited-distribution device handshake needs the target device online and signed in to Google is not spelled out.
- Community guides claim SideStore combined with LiveContainer removes the 3-app limit and expiry on iOS 26; this is unverified and no Apple statement on the longevity of SideStore/AltStore Classic was found.
- UK/Australia alternative-distribution status as of late Nov 2026 not confirmed.

## 3. Notifications with no third-party cloud

### Takeaway
On iOS, the only way to alert a device whose app is not running without Apple's push service is Local Push Connectivity (NEAppPushProvider), which works only on designated Wi-Fi networks and needs an entitlement that Apple must grant; everything else — native APNs, Web Push for a Home Screen web app, even the self-hosted ntfy iOS app — passes a wake-up through Apple (the content can be encrypted or absent, but timing and sender metadata leave the home and the hub needs internet access). On Android a fully local design is straightforward: a foreground service holding a WebSocket to the hub, as Home Assistant's "persistent connection" and ntfy's "instant delivery" do, optionally exposed to other apps through UnifiedPush.

### Cited Findings

**iOS — is APNs mandatory?**
- Apple positions Local Push Connectivity as the APNs substitute: "Provide functionality similar to Apple Push Notification Service when access to the wider internet is unavailable"; the system launches the app's NEAppPushProvider extension when the device joins a Wi-Fi network whose SSID matches the configured list, and it keeps running while the device stays on it; the extension should only deliver local notifications and CallKit alerts. — [Apple, Local push connectivity](https://developer.apple.com/documentation/networkextension/local-push-connectivity) [P]
- It requires the `com.apple.developer.networking.networkextension` entitlement with the `app-push-provider` value: "Request this entitlement from the Entitlement Request Page." — [Apple, Local push connectivity](https://developer.apple.com/documentation/networkextension/local-push-connectivity) [P]
- Forum reports: one developer of a home-automation app says the entitlement request was denied three times; another was approved for development/testing only and told to re-apply with a product description; DTS says approval time is unpredictable. — [Apple Developer Forums 819261](https://developer.apple.com/forums/thread/819261) [snippet]; [Apple Developer Forums 834979](https://developer.apple.com/forums/thread/834979) [snippet]
- Reliability: a Nov 2025 thread reports the provider being stopped (`unrecoverableNetworkChange` / `noNetworkAvailable`) after the app was backgrounded while still on the device's Wi-Fi; the Apple engineer said this "should not be happening" and asked for a bug report, but gave no lifecycle guarantee. — [Apple Developer Forums 807012](https://developer.apple.com/forums/thread/807012) [P]
- How Home Assistant implements "local push": notifications are delivered over the Home Assistant WebSocket API "rather than Apple Push Notification Service or Firebase Cloud Messaging"; on iOS it works only via the Internal URL with the home Wi-Fi SSIDs configured ("an operating system limitation"), keeps an ongoing connection with slightly higher battery use, and is exempt from rate limits (iOS/macOS since 2021.7, Android since 2022.2). The iOS app implements it with a push-provider extension added in 2021. — [Home Assistant Companion docs, Local Push](https://companion.home-assistant.io/docs/notifications/notification-local) [P]; [HA iOS source mirror](https://git.sudo.is/home-assistant/iOS/src/branch/master/Sources/Extensions/PushProvider/Resources) [snippet]
- Home Assistant's default (non-local) path uses Google's Firebase Cloud Messaging: content is not stored, but "Notification contents are not encrypted on Firebase, so Google could process them"; limit of 500 notifications per device per day. — [Home Assistant Companion docs, notification details](https://companion.home-assistant.io/docs/notifications/notification-details) [P]
- A free Apple Personal Team cannot use remote push at all; local notifications still work. — [Expo blog, 2 Nov 2026](https://expo.dev/blog/apple-developer-program-explained-free-vs-paid.md) [S]

**iOS — Web Push for a PWA: what passes through Apple**
- Web Push uses Apple's push service; the hub must be able to reach `https://*.push.apple.com`; no developer account is needed. The hub sends an encrypted payload (max 4 KB) to the subscription endpoint with headers Apple can read: `Authorization` (VAPID JWT and public key; the JWT subject must be a URL or `mailto:`), `TTL`, optional `Topic`, and `Urgency`. Apple may store an undelivered notification "for 30 days or fewer". — [Apple docs](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) [P]
- Web Push payloads must be encrypted so the push service cannot read them; the push service sees the delivery instructions (time-to-live, urgency, topic). — [web.dev](https://web.dev/articles/push-notifications-how-push-works) [P]

**iOS — self-hosted ntfy**
- "It is impossible to implement instant push notifications without a central server" on iOS: a self-hosted ntfy server forwards a poll request to ntfy.sh, which relays it through Firebase/APNs; the request "contains only the message ID ... and the SHA256 checksum of the topic URL", and the phone then fetches the real message from the user's own server. Without this upstream, delivery "can take hours" (roughly 20–30 minutes for an actively used phone). — [ntfy config docs](https://docs.ntfy.sh/config/) [P]

**Android**
- ntfy: FCM is "the only Google approved way" to push to Android, but ntfy's "instant delivery" keeps a persistent connection "achieved with a foreground service, which you'll see as a permanent notification" and works in doze mode; the app "won't use Firebase for any self-hosted servers, and not at all in the F-Droid flavor". — [ntfy phone docs](https://docs.ntfy.sh/subscribe/phone/) [P]
- Home Assistant Android: keeps the WebSocket alive behind a persistent notification on a "Persistent Connection" channel; for the minimal (Google-free) flavor the setting should be "Always", with background access granted. — [Home Assistant Companion docs, Local Push](https://companion.home-assistant.io/docs/notifications/notification-local) [P]
- UnifiedPush: a "distributor" app receives pushes and hands them to other apps; Android distributors include ntfy and Sunup (Mozilla autopush), both self-hostable, NextPush (Nextcloud) and Conversations (XMPP). The page lists no iOS distributor. — [UnifiedPush distributors](https://unifiedpush.org/users/distributors/) [P]
- OS constraints on the foreground service: since Android 14 every foreground service must declare a type; `dataSync` services of apps targeting Android 15+ are limited to 6 hours per 24 hours and cannot start from `BOOT_COMPLETED`; `specialUse` covers "valid foreground service use cases that aren't covered by the other types" (reviewed only when submitting to Google Play); `remoteMessaging` is defined for transferring text messages between devices. — [Android foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types) [P]; [Foreground service timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout) [snippet]
- Web Push in an Android PWA goes through the browser's push service (see question 1), so it is not cloud-free either. — [web.dev](https://web.dev/articles/push-notifications-how-push-works) [P]

### Inferences
- What leaves the home in each design (derived from the findings above):

| Design | Third party | Data that leaves the home | Other cost |
|---|---|---|---|
| Android app, foreground-service WebSocket to hub | none | nothing | permanent notification, battery, sideloaded app; away from home needs a VPN |
| In-app WebSocket while the app/PWA is open (any OS) | none | nothing | nothing arrives once the app is backgrounded |
| iOS Local Push Connectivity | none at runtime | nothing | paid Apple programme plus Apple-approved entitlement; home Wi-Fi only |
| iOS/Android Web Push from the hub | Apple / Google / Mozilla push service | encrypted payload (unreadable), plus sender IP, VAPID key and contact, device endpoint, size, time, TTL/urgency/topic | hub needs outbound internet; visible notification mandatory on iOS |
| Content-free wake-up (ntfy style) | ntfy.sh then Firebase/APNs | topic hash, message ID, timing | phone must then reach the hub (LAN or VPN) to fetch content |
| Self-hosted ntfy without upstream on iOS | none | nothing | delays of minutes to hours |
| Native APNs/FCM via someone else's relay (Home Assistant default) | relay operator plus Google/Apple | notification text readable by Google on the FCM leg | not applicable to a self-built hub without its own Apple/Firebase credentials |

- For iOS the pragmatic "least-cloud" option is Web Push from the hub straight to Apple with the standard encrypted payload: no account, no fee, and Apple learns only that an event happened and when. If even timing metadata is unacceptable, iOS devices can only be notified while the app is open or via a wall panel/another channel.
- Local Push Connectivity is unlikely to be obtainable for a personal project and is unavailable on a free team, so it should not be planned on.
- On Android, a sideloaded personal app is not subject to Play review, so the `specialUse` foreground-service type is the natural fit for a persistent hub connection; avoid `dataSync` because of the 6-hour cap.

### Gaps
- No primary statement on what APNs retains or logs for Web Push requests.
- Whether Apple grants the Local Push Connectivity entitlement to individuals for personal home use is known only anecdotally.
- Whether Declarative Web Push changes the encryption or metadata picture was not verified.
- OEM battery-management behaviour that kills foreground services on some Android brands was not researched.

## 4. HTTPS on a home LAN without cloud

### Takeaway
A secure context is required for the PWA features that matter (service worker, push, notifications, microphone, wake lock), so the hub needs a certificate the phones trust. There are two workable routes: a private CA (Caddy's internal CA, step-ca or mkcert) — fully offline and free, but every phone must install and explicitly trust the root, and on Android only browsers honour user-installed roots — or a real domain with Let's Encrypt DNS-01 certificates for names that resolve to private addresses — zero client setup, but it needs a registered domain, a DNS-API credential on the hub, internet access for renewals on a shortening schedule (45-day certificates by 2028), and every certificate is logged publicly.

### Cited Findings

**Why a secure context**
- `getUserMedia()` works only in secure contexts ("a page loaded using HTTPS or the `file:///` URL scheme, or a page loaded from `localhost`"); on plain HTTP `navigator.mediaDevices` is undefined. — [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) [P]
- MDN's list of features restricted to secure contexts includes Service Workers, Push API, Notifications API, `MediaDevices.getUserMedia`, Web Bluetooth, Screen Wake Lock, Web Crypto, Storage API and the Generic Sensor API. — [MDN, features restricted to secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts/features_restricted_to_secure_contexts) [P]
- Web Push from a self-hosted server requires the web app to be "served over HTTPS with a valid certificate". — [ntfy config docs](https://docs.ntfy.sh/config/) [P]

**Private CA options**
- mkcert creates a local CA and certificates for chosen names; it is "meant for development purposes, not production"; `rootCA-key.pem` "gives complete power to intercept secure requests from your machine". For phones: iOS — transfer `rootCA.pem` (AirDrop, email or HTTP), install the profile, then enable full trust; Android — install the CA and "enable user roots in your app's development build". — [mkcert README](https://github.com/FiloSottile/mkcert) [P]
- Caddy automatically serves IP addresses and local/internal hostnames with certificates from its own internal CA (a root plus an auto-renewed intermediate, stored under `pki/authorities/local`); it tries to install the root into the trust store of the machine it runs on, and installing it on other devices is the administrator's job. Names under `.localhost`, `.local`, `.internal` and `.home.arpa` cannot get publicly trusted certificates. — [Caddy, Automatic HTTPS](https://caddyserver.com/docs/automatic-https) [P]
- step-ca is an online CA for "secure, automated X.509 and SSH certificate management" that accepts "ACME challenge responses from any ACMEv2 client" and issues short-lived certificates with automated renewal; active revocation (CRL/OCSP) is very limited. — [smallstep step-ca docs](https://smallstep.com/docs/step-ca/) [P]

**Trusting a private root on iOS / iPadOS**
- A manually installed certificate profile "isn't automatically trusted for SSL": after installing the profile, go to Settings > General > About > Certificate Trust Settings and enable full trust for the root. Roots installed through Apple Configurator or MDM are trusted automatically. — [Apple Support 102390](https://support.apple.com/en-us/102390) [P]
- TLS server certificates on iOS 13+ must use RSA keys of at least 2048 bits, a SHA-2 signature, the DNS name in the SubjectAltName (CommonName is ignored), and — if issued after 1 July 2019 — the serverAuth EKU and a validity of 825 days or fewer. — [Apple Support 103769](https://support.apple.com/en-us/103769) [P]
- The newer 398-day limit "will not affect certificates issued from user-added or administrator-added Root CAs". — [Apple Support 102028](https://support.apple.com/en-us/102028) [P]

**Trusting a private root on Android**
- "By default, secure connections ... from all apps trust the pre-installed system CAs, and apps targeting Android 6.0 (API level 23) and lower also trust the user-added CA store by default." Apps targeting API 24+ must opt in via `<certificates src="user"/>` or bundle the CA as a raw resource; `debug-overrides` trust anchors apply only to debuggable builds. Android 17 (API 37) enables Certificate Transparency checks by default, but not for user or bundled trust anchors. — [Android network security configuration](https://developer.android.com/privacy-and-security/security-config) [P]
- Field reports: Chrome on Android accepts a CA installed in the Android user store, whereas Firefox for Android needs its hidden "Use third party CA certificates" setting and users still report failures. No official Chrome statement was found. — [Fenix issue 16993](https://github.com/mozilla-mobile/fenix/issues/16993) [snippet]

**Public domain + Let's Encrypt DNS-01**
- DNS-01 proves control by a TXT record at `_acme-challenge.<domain>`; it supports wildcards and "can validate domains whose web servers aren't exposed to the public internet"; drawbacks: DNS API credentials stored on the server are risky, the DNS provider may lack an API, and it cannot validate IP addresses (page updated 12 Feb 2026). — [Let's Encrypt challenge types](https://letsencrypt.org/docs/challenge-types/) [P]
- Caddy performs the DNS challenge through community-maintained DNS-provider plugins; wildcard certificates from Let's Encrypt require it. — [Caddy, Automatic HTTPS](https://caddyserver.com/docs/automatic-https) [P]
- Certificate lifetimes are shrinking: Let's Encrypt's opt-in `tlsserver` profile issues 45-day certificates from 13 May 2026; the default profile moves to 64 days on 10 Feb 2027 and to 45 days on 16 Feb 2028; optional 6-day certificates exist. A DNS-PERSIST-01 challenge (a TXT record that stays unchanged across renewals) was expected in 2026 but still needed IETF and CA/Browser Forum ratification. — [Let's Encrypt, From 90 to 45](https://letsencrypt.org/2025/12/02/from-90-to-45) [snippet]; [heise](https://heise.de/-11100410) [snippet]
- Let's Encrypt "submits all certificates we issue to CT logs". — [Let's Encrypt CT logs](https://letsencrypt.org/docs/ct-logs/) [P]

**Naming: `.local` vs `home.arpa` vs `.internal`**
- `home.arpa.` is the IETF special-use domain for "non-unique use in residential home networks" (RFC 8375, 2018); a host using a resolver other than the home network's may be unable to resolve it. — [RFC 8375](https://www.rfc-editor.org/rfc/rfc8375) [snippet]
- ICANN's board reserved `.internal` for private use on 29 July 2024. — [CircleID](https://circleid.com/posts/20240810-icann-reserves-.internal-domain-for-private-use) [snippet]; [IANA proposal](https://www.iana.org/news/2024/proposed-private-use-tld) [snippet]
- `.local` is mDNS (RFC 6762). Android's system resolver gained `.local` mDNS resolution in November 2021, but not over VPN or mobile-data connections; Chrome delegates `.local` to the OS; user reports are mixed across devices. — [Android DNS Resolver docs](https://source.android.com/docs/core/ota/modular-system/dns-resolver) [snippet]; [chromium-discuss](https://groups.google.com/a/chromium.org/g/chromium-discuss/c/6b0vVreNTvQ) [snippet]
- On iOS, resolving a `.local` name from native code requires the Local Network permission; Safari/WKWebView traffic does not. — [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) [P]

**Browser Local Network Access (LNA) changes, 2025–2026**
- Chrome's LNA permission prompt launched in Chrome 142 (announced 29 Sep 2025). It gates requests from public sites to local-network or loopback addresses and can only be requested from secure contexts; requests "from a local server to other local servers" were not covered in the first milestone. "Local" means RFC 1918, link-local and IPv6 ULA addresses. — [Chrome blog, Local Network Access](https://developer.chrome.com/blog/local-network-access) [P]
- Current Chrome guidance: two permissions (`local-network`, `loopback-network`); once granted, `http://` local endpoints are exempt from mixed-content blocking for private-IP literals, `.local` names or `fetch()` with `targetAddressSpace`; `ws://` from an HTTPS page is exempt only for IP literals, `localhost` and `.local` — "for custom DNS names, use `wss://`". Public names that resolve to local addresses are not exempt. — [Chrome LNA guide](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access) [P]
- WebSocket connections to local addresses are being brought under the same prompt ("Will ship enabled for all users"; flag notice Feb 2026). — [blink-dev, Intent to Ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/O6GMKt44Ups) [snippet]
- Firefox shows a comparable local-network permission prompt, with default enablement rolling out gradually from Firefox 151 according to one revision of the support article; Firefox for Android has the same prompts. — [Mozilla Support](https://support.mozilla.org/en-US/kb/control-personal-device-local-network-permissions-firefox) [snippet]

### Inferences
- Route comparison (derived from the findings above):

| Route | Works | Does not / pitfalls | Hidden dependency or cost |
|---|---|---|---|
| Private CA (Caddy internal / step-ca) | Fully offline; any name (`home.arpa`, `.internal`) or IP; long-lived root | Per-device root install; two-step trust on iOS; Android apps ignore user roots unless opted in; Firefox Android unreliable | Guarding the root key; re-issuing leaf certs (keep them at 825 days or fewer for iOS) |
| mkcert | Quick start | Not meant for production; no renewal automation | Same trust steps as any private CA |
| Public domain + DNS-01 | No client setup; works in every browser and app | Renewal needs internet; certificate names appear in public CT logs; DNS-01 cannot cover bare IPs | Domain registration fee; DNS provider with an API; API credential stored on the hub; 45-day lifetimes by 2028 |
| Plain HTTP on the LAN | Simple | No service worker, push, microphone or wake lock; cleartext blocked by default in Android apps | none |

- The private-CA route is the only one consistent with "no cloud, no recurring cost"; its price is a one-time trust ceremony per device. The public-domain route is easier for guests' devices but makes a public CA, a registrar and a DNS provider part of the home's availability chain — if the internet link is down longer than a certificate's remaining life, the PWA loses its secure context.
- If the PWA is served by the hub itself from a private address, its API calls are same-origin and local-to-local, so Chrome's public-to-local prompt should not appear; a publicly hosted page calling the hub would trigger it.
- Prefer a unicast DNS name (`hub.home.arpa` or similar served by the router) for the certificate rather than relying on `.local`, because Android mDNS resolution is inconsistent and absent over VPN; using `wss://` everywhere avoids Chrome's mixed-content edge cases.

### Gaps
- Whether DNS-PERSIST-01 had actually shipped by Nov 2026 was not confirmed.
- No official Chrome-for-Android statement on trusting user-installed CAs; iOS Home Screen web-app behaviour on a user-trusted root (service worker, push) was not device-verified.
- Home-router DNS-rebinding protection, which can block public names resolving to private addresses, was not researched.
- Caddy's internal certificate lifetimes and its ACME-server feature were not confirmed from the page read; no Safari LNA plans were found.

## 5. Remote access from outside the home with no subscription

### Takeaway
If the home has a public IPv4 address or usable inbound IPv6, a self-hosted WireGuard endpoint on the router or hub is the only option with no third party at all. Behind carrier-grade NAT without IPv6, some publicly reachable machine must help: either one you rent (a VPS as WireGuard relay or as a Headscale/NetBird control server — a recurring fee) or one a company runs for free (Tailscale's Personal plan: free, six users, but its coordination server and login provider become dependencies). Traffic is end-to-end encrypted in every case; the options differ in who can see connection metadata and who can admit devices.

### Cited Findings
- Plain WireGuard "does not provide peer discovery or a relay service"; a mesh VPN fits when both ends are behind CGNAT and no public endpoint is controlled. — [ZimaSpace comparison](https://shop.zimaspace.com/blogs/product-comparisons/wireguard-server-vs-mesh-vpn-cgnat) [snippet]
- VPS relay pattern: the home device dials out to a public VPS and keeps the tunnel open; `PersistentKeepalive = 25` on the home side is described as critical. — [Hetzner community tutorial](https://community.hetzner.com/tutorials/bypass-cgnat-with-a-wireguard-vps-relay/) [snippet]
- IPv6: OpenWrt users behind CGNAT report reaching their home WireGuard server over IPv6 alone (firewall rule plus a DNS name for the IPv6 address); a build log describes routing a /48 through a roughly 3 USD/month VPS. — [OpenWrt forum](https://forum.openwrt.org/t/possible-to-connect-via-wiregaurd-to-router-behind-a-cgnat/211445) [snippet]; [build log](https://marfillaster.github.io/vps-ipv6-cgnat-mikrotik/) [snippet]
- WireGuard client UX: the iOS/macOS apps support on-demand activation with trusted-SSID exclusion; a 2021 mailing-list thread says the Android app lacks an equivalent, and a third-party F-Droid helper (WGControl) toggles the tunnel by Wi-Fi network. — [OPNsense forum](https://forum.opnsense.org/index.php?topic=32706.0) [snippet]; [WireGuard mailing list](https://lists.zx2c4.com/pipermail/wireguard/2021-November/007293.html) [snippet]; [WGControl on F-Droid](https://f-droid.org/packages/org.supersane.wgcontrol/) [snippet]
- Tailscale Personal plan (page read Nov 2026): 0 USD, "Free forever", up to 6 users, unlimited user devices, 50 tagged resources; "only suitable for non-commercial use". On 8 Apr 2026 Tailscale retired Personal Plus and said the Personal plan is "getting better and staying free". — [Tailscale pricing](https://tailscale.com/pricing) [P]; [Tailscale blog, 8 Apr 2026](https://tailscale.com/blog/pricing-v4) [P]
- Tailscale trust model per its own material: the coordination server holds the device registry, public keys and policy but no private keys, so it cannot decrypt traffic; DERP relays carry only end-to-end encrypted packets; tailnet lock prevents the coordination server from adding nodes on its own. A user thread notes residual trust in the coordination server remains. — [Tailscale security](https://tailscale.com/security) [snippet]; [Tailscale blog, tailnet lock](https://tailscale.com/blog/tailnet-lock) [snippet]; [Tailscale forum](https://forum.tailscale.com/t/tailscale-security-what-if-the-coordination-server-goes-rogue/5015) [snippet]
- Headscale is "an open source, self-hosted implementation of the Tailscale control server" for a single tailnet, aimed at personal use; it needs a server with a public IP (dual-stack recommended), HTTPS on tcp/443, and udp/3478 if the embedded DERP relay is enabled. Official Tailscale clients on Android, iOS, macOS, Windows and Linux work (the project targets the last 10 client releases). Supported: MagicDNS, ACLs, subnet routers, exit nodes, Taildrop, Tailscale SSH, embedded DERP, peer relays; Funnel and Serve are tracked as open issues. — [Headscale](https://headscale.net/stable/) [P]; [requirements](https://headscale.net/stable/setup/requirements/) [P]; [clients](https://headscale.net/stable/about/clients/) [P]; [features](https://headscale.net/stable/about/features/) [P]
- NetBird self-hosted needs a public domain resolving to the VM, public TCP 443 and UDP 3478, and at least 1 CPU / 2 GB RAM; it deploys management, signal, relay, STUN and a dashboard, with an embedded identity provider so no external IdP is required. — [NetBird self-hosting quickstart](https://docs.netbird.io/selfhosted/selfhosted-quickstart) [P]
- ZeroTier: since v1.16.0 (Aug 2025) the network controller is under a commercial source-available licence and is no longer included in default builds; users reported the self-hosted controller API stopped working after upgrading. — [ZeroTier changelog 1.16.0](https://docs.zerotier.com/changelog/2025/08/21/zt1-v1.16.0) [snippet]; [ZeroTier forum](https://discuss.zerotier.com/t/zerotier-1-16-0-self-hosted-controller/28269) [snippet]

### Inferences
- Option comparison (derived from the findings above):

| Option | Behind CGNAT? | Third party involved | Recurring cost | Trust implication |
|---|---|---|---|---|
| WireGuard on router/hub, public IPv4 | no | none (perhaps dynamic DNS) | none | none |
| WireGuard over IPv6 | yes, if both ends have IPv6 and inbound UDP is allowed | ISP only | none | none |
| WireGuard via own VPS relay | yes | VPS provider | VPS fee | provider sees metadata; sees content too if the tunnel terminates on the VPS and inner traffic is not TLS |
| Tailscale Personal | yes | Tailscale plus the login identity provider | none (non-commercial) | they see device list, addresses and connection metadata; mitigated by tailnet lock |
| Headscale | only with a public host (VPS) | VPS provider | VPS fee | self-controlled control plane |
| NetBird self-hosted | only with a public host (VPS) | VPS provider | VPS fee, heavier stack | self-controlled |
| ZeroTier self-hosted controller | yes via relays | ZeroTier infrastructure and licence terms | none stated | licence change makes this the least future-proof |

- Under a strict reading of "no subscription", only direct WireGuard (public IPv4 or IPv6) and Tailscale's free tier qualify; a VPS is a subscription in all but name. Tailscale's free tier trades money for a dependency on a company's policy.
- Always-on VPN on an Android phone also extends the cloud-free notification design of question 3 to times away from home; on iOS on-demand WireGuard gives the PWA reachability but not background notifications.
- Keeping the hub's HTTPS name and certificate identical inside and outside (the VPN simply routes to the same private address) avoids a second trust configuration.
- Scope update (rented flat, ISP/building router not configurable): treat the home as having no inbound IPv4 even if the ISP does not use CGNAT, because no port can be forwarded on the upstream router. The "WireGuard on router/hub, public IPv4" row is then unavailable and the choice narrows to an outbound-initiated tunnel — see question 9.

### Gaps
- Whether mobile carriers and guest Wi-Fi provide the IPv6 needed to reach an IPv6-only home endpoint was not researched.
- Which Tailscale features (Funnel, HTTPS certificates, peer relays, tailnet lock) are included in the free plan was not confirmed line by line.
- Headscale's default use of Tailscale-operated DERP relays, NetBird's licence terms and the status of third-party ZeroTier controllers after 1.16 were not confirmed.
- No 2026 source on whether the official WireGuard Android app has gained on-demand rules.

## 6. Security baseline for a DIY IoT network

### Takeaway
Segment the network (a dedicated IoT SSID/VLAN with firewall rules so that only the hub can initiate connections to devices, and IoT devices have no internet access), authenticate and encrypt each hop (MQTT with per-device credentials and topic ACLs, TLS where memory allows, or ESPHome-style Noise encryption, which costs far less than TLS on an ESP32), and protect firmware updates (ESPHome 2026.9 encrypts OTA; ESP-IDF secure boot and flash encryption address physical attacks). EU rules (RED cybersecurity since August 2025, CRA reporting since September 2026, full CRA in December 2027) bind manufacturers who place products on the market; for a hobbyist their effect is indirect — on which devices can still be bought and reflashed.

### Cited Findings

**Segmentation**
- The NSA's home-network guidance (Feb 2023) recommends wireless network segmentation with at least three networks: primary, guest and IoT. — [NSA Cybersecurity Information Sheet](https://media.defense.gov/2023/Feb/22/2003165170/-1/-1/0/CSI_BEST_PRACTICS_FOR_SECURING_YOUR_HOME_NETWORK.PDF) [snippet]; [NSA press release](https://www.nsa.gov/Press-Room/Press-Releases-Statements/Press-Release-View/Article/3304674/nsa-releases-best-practices-for-securing-your-home-network/) [snippet]
- Segments alone do not isolate: firewall rules between segments are needed, with explicit exceptions such as a hub on the main network that must reach IoT devices; isolation should be tested; some IoT devices misbehave with VLAN setups, where a separate access point can be simpler. — [Bitdefender guide](https://www.bitdefender.com/en-gb/blog/hotforsecurity/network-segmentation) [snippet]

**MQTT authentication, ACLs, TLS**
- Mosquitto 2.0+ requires authentication options to be chosen explicitly before clients can connect; options are a password file (`mosquitto_passwd`), the Dynamic Security plugin (clients, groups and roles administered remotely), or other plugins; `per_listener_settings` allows different methods per listener; authentication should be combined with topic access control. — [Mosquitto authentication methods](https://mosquitto.org/documentation/authentication-methods/) [P]
- Cost of TLS on ESP32 (ESP-IDF v5.5 docs, HTTPS client example with server validation): about 42 KB heap per TLS connection by default, 38.5 KB without keeping the peer certificate, and about 22 KB with dynamic TX/RX buffers; hardware acceleration exists for SHA, AES and bignum; TLS 1.3 is fully supported from Mbed TLS 3.6. — [ESP-IDF Mbed TLS docs](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/protocols/mbedtls.html) [P]

**ESPHome API encryption and OTA**
- ESPHome 2026.1.0 (21 Jan 2026): "API password authentication has been removed and API encryption is now required" — password auth "only verified identity while all data was still transmitted in plaintext"; the replacement is a Noise `encryption:` key (`openssl rand -base64 32`). OTA: MD5 authentication removed, "SHA256 is now mandatory"; ESP32 (ESP-IDF) gains automatic OTA rollback. — [ESPHome 2026.1.0](https://esphome.io/blog/2026/01/21/esphome-2026-1/) [P]
- ESPHome 2026.9.0 (16 Sep 2026): OTA updates are encrypted with Noise (ChaCha20-Poly1305). Previously "the firmware image went over the network unencrypted, and it can contain your WiFi password and API encryption key"; the OTA password only authenticated the uploader. With `encryption:` set, the device rejects unencrypted updates; the unencrypted OTA path is removed in 2027.3.0. — [ESPHome 2026.9.0](https://esphome.io/blog/2026/09/16/esphome-2026-9/) [P]
- Measured cost of Noise API encryption after the 2026.9 optimisation: ESP32 37.7 KB flash, 32 B static RAM, about 46 ms handshake; ESP8266 41.9 KB flash, about 300 ms handshake. The same release shuts down the Wi-Fi provisioning access point when the provisioning window closes. — [ESPHome 2026.9.0](https://esphome.io/blog/2026/09/16/esphome-2026-9/) [P]
- Counter-example: the Ava Android voice satellite speaks the ESPHome protocol on a port "with no authentication, so it should only run on trusted local networks". — [Ava README](https://github.com/brownard/Ava) [P]

**OTA integrity and physical attacks**
- ESP-IDF Secure Boot v2 verifies the signed application "not only ... on every boot but also on each over the air (OTA) update"; it needs ESP32 chip revision v3.0 or later; enabling it is a one-time, irreversible step; Espressif recommends combining it with flash encryption and says OTA must use secure transport. — [ESP-IDF Secure Boot v2](https://docs.espressif.com/projects/esp-idf/en/stable/security/secure-boot-v2.html) [snippet]

**Secrets**
- Firmware images can embed the Wi-Fi password and API key; DNS-API credentials on a web server and a private CA's root key are high-value secrets. — [ESPHome 2026.9.0](https://esphome.io/blog/2026/09/16/esphome-2026-9/) [P]; [Let's Encrypt challenge types](https://letsencrypt.org/docs/challenge-types/) [P]; [mkcert README](https://github.com/FiloSottile/mkcert) [P]

**Regulation (only where it affects buying or flashing)**
- CRA dates: vulnerability/incident reporting (Article 14) applies from 11 September 2026; full application (essential requirements, conformity assessment, CE marking) from 11 December 2027 for units placed on the market from then. The "manufacturer" is whoever places the product on the EU market under its name; importers or distributors who rebrand or substantially modify count as manufacturers. — [Espressif, CRA obligations and deadlines (Sept 2026)](https://developer.espressif.com/blog/2026/09/esp32-cra-obligations-and-deadlines/) [P]
- The RED Delegated Act cybersecurity requirements (EN 18031) have been mandatory since August 2025 and remain applicable until the CRA takes over in December 2027. — [Eurofins/Würth slides](https://www.we-online.com/files/pdf1/eurofins-en18031-cra_wuerth-elektronik.pdf) [snippet]; [Espressif RED-DA guide](https://developer.espressif.com/blog/2025/04/esp32-red-da-en18031-compliance-guide/) [snippet]
- The European Commission states that only free and open-source software "supplied for distribution or use in the course of a commercial activity" is in scope of the CRA, and that non-monetised open-source software is not a commercial activity. — [European Commission, CRA and open source](https://digital-strategy.ec.europa.eu/en/policies/cra-open-source) [snippet]
- No source found says RED or the CRA requires blocking user-installed firmware; searches returned nothing on vendors citing these rules to lock devices. Practical flashing obstacles predate them: Tuya patched the over-the-air `tuya-convert` route years ago, and newer Tuya plugs use BK7231N chips that Tasmota does not support. — [blog, Oct 2025](https://neilturner.me.uk/2025/10/06/) [snippet]; [Home Assistant community thread](https://community.home-assistant.io/t/flashable-uk-smart-plugs/152702?page=8) [snippet]

### Inferences
- A baseline consistent with the findings: (1) IoT SSID/VLAN with default-deny inter-VLAN rules, hub-initiated connections only, no internet for IoT devices (provide local NTP/DNS); (2) broker with anonymous access off, one credential per device and ACLs limiting each device to its own topics; (3) transport encryption chosen by device class — full TLS is affordable on an ESP32 for one broker connection (22–42 KB heap), while a Noise/pre-shared-key scheme is the lighter choice and the direction ESPHome has taken; (4) OTA only from the hub, authenticated and encrypted, with rollback, and signed images plus secure boot where physical access is a concern; (5) secrets kept out of the repository and out of unencrypted firmware transfers.
- Building devices for one's own home is not "placing a product on the market", so the CRA and RED duties should not fall on the builder; this follows from the manufacturer definition and the Commission's open-source statement but no source addresses personal-use builds directly.
- Phone-app pairing: no authoritative source was consulted; a design in the spirit of the per-device keys above would be a one-time pairing code or QR shown on the LAN that yields a per-device revocable token, with authentication enforced even on the LAN and Origin checks on the WebSocket.
- For buying hardware, the safer assumption is to choose devices that are built on ESP chips and sold as flashable or pre-flashed, rather than counting on being able to reflash mass-market cloud devices.
- Scope update: because the ISP/building router cannot be configured, the segmentation in point (1) has to live on a user-owned router placed behind it; question 9 covers that topology. The hub laptop itself (question 10) holds the CA key, broker credentials and Wi-Fi keys, so its disk-encryption choice is part of this baseline.

### Gaps
- Whether ESPHome exposes secure boot, flash encryption or signed-OTA verification in its configuration was not confirmed.
- No MQTT-specific TLS measurements (heap, handshake time) for ESP32 or ESP8266 were found.
- No evidence either way on vendors locking firmware because of EN 18031 or the CRA; the NSA text was seen only via snippets, and NIST/CISA documents were not opened.
- API authentication and device-pairing best practice for a self-built hub was not researched from primary sources.

## 7. Voice from the phone

### Takeaway
Push-to-talk works from a PWA on both platforms as long as the page is a secure context: capture with `getUserMedia` and stream to the hub. Always-listening is in practice Android-only: open-source apps do on-device wake-word detection with a continuously running service (the Home Assistant Companion app from 2026.2.3, and Ava as an ESPHome-protocol satellite) at a noticeable battery cost, while iOS does not let a third-party app start recording from the background and Home Assistant's own iOS app offers no wake word, only button and shortcut triggers.

### Cited Findings
- Browser capture needs HTTPS: `getUserMedia()` is unavailable in insecure contexts and always requires user permission. — [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) [P]
- Safari 18.4 (31 Mar 2025) added WebM support to MediaRecorder and Ogg Opus support, and fixed re-prompting for microphone permission after same-origin navigation. — [Safari 18.4 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-18_4-release-notes) [P]
- Home Assistant Companion for Android: on-device wake-word detection (microWakeWord) from app version 2026.2.3, marked experimental; requires the app to be the default assistant; wake words "Hey Nabu", "Hey Jarvis", "Hey Mycroft"; works when locked or in the background; battery impact is high because third-party apps cannot use the low-power hardware that "Ok Google" uses; audio is sent to the server only after the wake word. — [Home Assistant, Assist on Android](https://www.home-assistant.io/voice_control/android/) [P]; [Home Assistant, wake words](https://www.home-assistant.io/voice_control/about_wake_word) [P]
- Wake-word engines: microWakeWord runs on ESP32-S3 and Android devices; openWakeWord runs on the server, is English-only and too large for low-power devices. — [Home Assistant, wake words](https://www.home-assistant.io/voice_control/about_wake_word) [P]
- Ava: an experimental, Apache-2.0 Android voice satellite using the ESPHome protocol (the phone listens on port 6053), with up to two on-device microWakeWord models, stop word, timers, announcements and a media player; Android 8+; designed for static wall panels; constant listening drains battery; the port is unauthenticated. — [Ava README](https://github.com/brownard/Ava) [P]
- Running the older Wyoming satellite with openWakeWord on Android through Termux gives mixed results (users report wake word or recording not working on some devices). — [Home Assistant community thread](https://community.home-assistant.io/t/how-to-run-wyoming-satellite-and-openwakeword-on-android/777571) [snippet]
- Android platform rule: a `microphone` foreground service cannot be created while the app is in the background, nor launched from a `BOOT_COMPLETED` receiver (with a few exceptions), because `RECORD_AUDIO` is a while-in-use permission. — [Android foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types) [P]
- iOS: an Apple engineer states an app "must be in the foreground to start recording"; with the audio background mode it can continue after moving to the background; starting from the background fails with `cannotStartRecording`, and Shortcuts or the Action Button cannot start a recording unless the app is active. — [Apple Developer Forums 674632](https://developer.apple.com/forums/thread/674632) [snippet]; [Apple Developer Forums 770556](https://developer.apple.com/forums/thread/770556) [snippet]
- Home Assistant on iPhone/iPad: Assist is started in-app, via a Shortcut, back tap, Action button, Control Center or Lock Screen control; there is no built-in wake word — the only hands-free route is iOS Voice Control with a custom phrase, which enables system-wide voice navigation. — [Home Assistant, Assist on Apple devices](https://www.home-assistant.io/voice_control/apple/) [P]

### Inferences
- For push-to-talk on a LAN, a WebSocket carrying short audio frames reuses the hub's existing API and is sufficient; WebRTC's extra machinery (NAT traversal, congestion control) solves problems a LAN or VPN link does not have. This is a design judgement, not a sourced finding.
- Old Android phones are the realistic always-listening satellites. If the self-built hub implemented the ESPHome voice-satellite protocol, Ava could be reused unchanged; the Home Assistant Companion wake word only talks to Home Assistant.
- Because the microphone service must be started while the app is visible, an Android satellite should run as a pinned, always-foreground kiosk app rather than rely on starting after boot.
- An old iPhone or iPad can only listen while an app or PWA is in the foreground (for example locked in with Guided Access and powered), with wake-word detection running inside that app.

### Gaps
- No source compared WebSocket and WebRTC latency for this use, and none verified long-running microphone capture in an iOS 26/27 Home Screen web app.
- Whether Ava works against a non-Home-Assistant server was not confirmed.
- Release dates and maintenance status of Ava and other apps (HAwake, Dashie) were not established.

## 8. Reusing old phones and tablets as wall panels, microphones or sensors

### Takeaway
For kiosk use, the best-known Android tool (Fully Kiosk Browser) is a paid, closed-source product, and the open-source field is unstable (WallPanel and KioskZen are archived; kiFOSSk and FreeKiosk were active in 2026); stock Android app pinning or iOS Guided Access can lock a browser or PWA with no extra software. Battery safety is the real risk of 24/7 charging: use a built-in 80% limit where the device has one, otherwise cycle charging with a smart plug driven by the reported battery level, keep the device cool and check for swelling, or use battery-less power. For sensors, Android apps can publish light, pressure, battery and camera-motion data to a local hub; browser sensor APIs are too limited to rely on.

### Cited Findings

**Kiosk software**
- Fully Kiosk Browser: PLUS licence is a one-time 8.90 EUR (10.99 USD) plus tax per device; an optional Fully Cloud subscription costs up to 1.18 EUR/month per device; features include motion detection, REST and JavaScript APIs, MQTT and remote admin. The vendor page does not state the source model. — [Fully Kiosk](https://www.fully-kiosk.com/) [P]
- A competing project's comparison lists Fully Kiosk as closed source and paid per device; Home Assistant's Fully Kiosk integration needs Remote Admin, a paid PLUS feature. — [FreeKiosk repository](https://github.com/RushB-fr/freekiosk) [snippet]; [Home Assistant integration docs](https://www.home-assistant.io/integrations/fully_kiosk) [snippet]
- WallPanel (Apache-2.0): kiosk browser with MQTT and HTTP control (URL, brightness, wake), sensor reporting (temperature, light, pressure, battery), camera motion/face detection, QR reading, an MJPEG stream server and text-to-speech; Android 4.4+. The repository has been archived and read-only since 5 May 2025 and the maintainer is looking for a successor. — [WallPanel repository](https://github.com/TheTimeWalker/wallpanel-android) [P]
- KioskZen (GPL-3.0): fullscreen kiosk with a choice of GeckoView or Android WebView, auto-start after boot and admin password; the repository is archived and "will not receive further updates". — [KioskZen repository](https://github.com/exraaaa/KioskZen) [P]
- kiFOSSk (MIT): "Lightweight FOSS kiosk browser for dashboards", can act as the home launcher and start on boot without Device Owner setup; version 1.1.4 was added to F-Droid on 27 Oct 2026; Android 7.0+. No sensor or remote-control features are listed. — [F-Droid listing](https://f-droid.org/packages/com.shinydiscoballsdev.kifossk/) [P]
- FreeKiosk (MIT) describes itself as a free Fully Kiosk alternative with a REST API and MQTT; other 2026 community projects include Kite AOS and Dashie (the latter with on-device voice). All claims are self-reported. — [FreeKiosk repository](https://github.com/RushB-fr/freekiosk) [snippet]; [Kite AOS thread](https://community.home-assistant.io/t/kite-aos-open-source-kiosk-for-home-assistant/1016206) [snippet]; [Dashie thread](https://community.home-assistant.io/t/dashie-open-source-fully-kiosk-alternative-for-hosting-ha-dashboards-with-on-device-voice/1022978) [snippet]
- Android app pinning (Settings > Security > App pinning) keeps one app on screen until unpinned, and requires the PIN, pattern or password to unpin. — [Google Android Help](https://support.google.com/android/answer/9455138) [P]
- iOS/iPadOS Guided Access restricts the device to a single app, with a passcode or Face ID/Touch ID to exit; it can disable hardware buttons, ignore touch in chosen areas and set the display auto-lock behaviour; Crash Detection and Emergency Services are unavailable during a session. — [Apple Support 111795](https://support.apple.com/en-us/111795) [P]

**Battery safety on permanent power**
- iPad: an "80% Limit" stops charging at about 80% and resumes at 75%, with occasional full charges for calibration; supported on iPad Pro (M4) and later, iPad Air (M2) and later, iPad mini (A17 Pro) and iPad (A16). Apple advises against using or charging above 35 °C ambient. — [Apple Support 118418](https://support.apple.com/en-us/118418) [P]; [iPad User Guide, Set a charge limit](https://support.apple.com/guide/ipad/set-a-charge-limit-ipadb3190c30/ipados) [snippet]
- iPhone: an adjustable Charge Limit (80–100%) exists on iPhone 15 and later; older iPhones offer only Optimized Battery Charging, with no cap described. — [Apple Support 108055](https://support.apple.com/en-us/108055) [P]
- Android: Pixels gained a fixed "Limit to 80%" option in the Android 15 December 2024 update, plus battery bypass; Samsung offers a battery-protection cap (80% in current One UI, 85% on older versions). — [9to5Google](https://9to5google.com/2024/12/18/charging-optimization-saves-pixel-battery-heres-how/) [snippet]; [GSMArena](https://www.gsmarena.com/google_pixels_got_80_battery_charge_limit_and_battery_bypass_with_the_latest_update-news-65708.php) [snippet]; [Chargie blog](https://chargie.org/android-15-80-charging-limit/) [snippet]
- Community experience: users report wall-mounted tablets whose batteries swelled until the screen lifted after being left plugged in; a common mitigation is a smart plug switched by automation to cycle the battery (for example charge to about 80%, discharge to 20–40%), especially on devices with no charge-limit setting; others remove the battery or use battery-less/PoE tablets. — [openHAB thread, bloated battery](https://community.openhab.org/t/bloated-battery-in-tablet-fire-hazard/145821) [snippet]; [Home Assistant thread, smart charging vs smart outlet](https://community.home-assistant.io/t/always-on-tablet-better-to-use-its-built-in-smart-charging-or-connect-to-a-smart-outlet/761460) [snippet]; [openHAB thread, tablets without battery](https://community.openhab.org/t/android-tablets-without-battery/150373) [snippet]

**Exposing phone sensors to a local hub**
- Sensor Server (GPL-3.0, on F-Droid and GitHub): the phone runs a WebSocket server (`ws://<ip>:<port>/sensor/connect?type=<sensor>`) streaming JSON readings from all available sensors (accelerometer, gyroscope, light, pressure, temperature, GPS, touch), discoverable via mDNS; no camera or microphone (a separate WebsocketCAM project covers the camera). — [SensorServer repository](https://github.com/umer0586/SensorServer) [P]
- WallPanel publishes light, pressure, temperature and battery readings and camera-based motion/face events over MQTT or HTTP, and serves an MJPEG camera stream (project archived). — [WallPanel repository](https://github.com/TheTimeWalker/wallpanel-android) [P]
- In the browser, the AmbientLightSensor API is experimental with "limited availability" ("does not work in some of the most widely-used browsers"), needs a secure context and a sensor permission. — [MDN AmbientLightSensor](https://developer.mozilla.org/en-US/docs/Web/API/AmbientLightSensor) [P]
- Microphone reuse is covered by the voice-satellite apps in question 7 (Ava; Home Assistant Companion). — [Ava README](https://github.com/brownard/Ava) [P]

### Inferences
- The zero-dependency wall panel is the hub's own PWA in the stock browser, locked with app pinning (Android) or Guided Access (iOS) and kept awake with the Screen Wake Lock API; this gives a display but no sensors or remote screen control.
- Sensors, remote wake/brightness and an always-on microphone require an Android app. Given how many open-source kiosk projects have been archived, a small self-built Android shell (WebView plus a foreground service publishing sensors over the hub's WebSocket) may prove more durable than depending on any one of them; it would be installed via ADB, which the Android verification programme leaves untouched.
- Since the hub already switches sockets, closing the loop on battery care is natural: the panel reports its battery level and the hub cycles the charger's plug. Devices with a native 80% cap (recent iPads, iPhone 15+, Pixels, recent Samsungs) are preferable; old iPhones and iPads without the cap need the smart-plug approach or should not be left on permanent charge.
- Old devices on Android 7 or earlier, or without Google certification, are outside Google's developer-verification enforcement, which helps for kiosk hardware but also means no security updates — keep them on the isolated IoT segment.

### Gaps
- No manufacturer or laboratory source was found for smart-plug cycling thresholds; the practice rests on community reports.
- Feature and licence claims for FreeKiosk, Kite AOS and Dashie are self-reported and were not read from the repositories; Fully Kiosk's closed-source status comes from a competitor's table, not the vendor.
- No way was found to expose iPhone/iPad sensors to a local hub without a native app; browser access to battery level and motion sensors on each platform was not checked.
- Sensor Server's background behaviour and latest release date were not shown on the page read.

## 9. (Added) An isolated IoT network on a small user-owned OpenWrt-capable router behind an ISP or building router you cannot configure

### Takeaway
Put a user-owned router in router (NAT) mode behind the ISP router and run everything behind it: a trusted network for phones and the hub laptop, and a separate IoT zone with no forwarding to the internet. The resulting double NAT is harmless for outbound traffic and usefully shields the home from the building network, but it removes any chance of inbound port forwarding, so self-hosted WireGuard cannot accept connections directly; remote access has to be an outbound-initiated tunnel (a WireGuard client dialling a rented VPS, or a NAT-traversing mesh such as Tailscale acting as a subnet router). mDNS does not cross between the zones unless a reflector is run, so discovery should either be reflected deliberately or avoided with fixed addresses and DNS names.

### Cited Findings

**Hardware and firmware (state Nov 2026)**
- OpenWrt's current stable release is 25.12.6 (18 Oct 2026); the old stable 24.10.8 (24 Jul 2026) is "considered outdated" but still receives limited security and bug fixes. — [OpenWrt downloads](https://downloads.openwrt.org/) [P]
- OpenWrt's main source tree contains build targets (MediaTek Filogic family) for GL.iNet GL-MT6000, GL-MT3000, GL-MT2500, GL-MT3600BE, GL-X3000, GL-XE3000, GL-BE10000 and GL-BE14000, and for Cudy WR3000 (v1 and E/H/P/S/U variants), TR3000, M3000, AP3000 (including Outdoor and Wall), RE3000, WBR3000UAX and P2. (Only the first part of the file was read; other models may be defined further down.) — [OpenWrt source, filogic.mk](https://raw.githubusercontent.com/openwrt/openwrt/main/target/linux/mediatek/image/filogic.mk) [P]
- Cudy publishes its own "OpenWrt intermediate firmware" that removes the signature check so OpenWrt can be flashed from the stock web UI. It warns that AX3000-series units with serial numbers starting 2543 or later use a new flash chip — older intermediate or OpenWrt images "will stop these devices from booting" — and says OpenWrt 24.10.5 or newer works (update dated 24 Dec 2025). Cudy gives no warranty for products running non-Cudy software. — [Cudy, OpenWrt software download](https://www.cudy.com/blogs/faq/openwrt-software-download) [P]
- The NSA's home-network guidance recommends using "a personally-owned routing device that connects to the ISP-provided modem/router". — [NSA Cybersecurity Information Sheet](https://media.defense.gov/2023/Feb/22/2003165170/-1/-1/0/CSI_BEST_PRACTICS_FOR_SECURING_YOUR_HOME_NETWORK.PDF) [snippet]

**Double NAT**
- Double NAT is two NATs chained; the extra layer is mostly invisible to outbound connections, but "The big thing that breaks is our port mapping protocols." Carrier-grade NAT is the ISP-run version of the same thing. — [Tailscale, How NAT traversal works](https://tailscale.com/blog/how-nat-traversal-works) [P]
- UPnP IGD, NAT-PMP and PCP let a client ask its router to "forward a WAN port"; they are not always available and one UPnP checkbox often disables all three. — [Tailscale, How NAT traversal works](https://tailscale.com/blog/how-nat-traversal-works) [P]

**Firewall zones: blocking IoT-to-internet traffic**
- OpenWrt's default firewall: global defaults input REJECT, output ACCEPT, forward REJECT; zone `lan` accepts input, output and forward; zone `wan` rejects input, drops forward and masquerades (NAT); the only inter-zone forwarding defined is `lan` → `wan`. — [OpenWrt firewall4 default configuration](https://raw.githubusercontent.com/openwrt/firewall4/master/root/etc/config/firewall) [P]
- OpenWrt's own interface text: zone `input`/`output` "set the default policies for traffic entering and leaving this zone", `forward` covers "forwarded traffic between different networks within the zone", and inter-zone forwarding "is unidirectional, e.g. a forward from lan to wan does not imply a permission to forward from wan to lan". — [LuCI firewall zone help text](https://raw.githubusercontent.com/openwrt/luci/master/applications/luci-app-firewall/htdocs/luci-static/resources/view/firewall/zones.js) [P]

**mDNS across segments**
- mDNS is link-scoped by design: `.local` names "are meaningful only on the link where they originate", queries go to the link-local multicast address 224.0.0.251 (or FF02::FB) on UDP 5353, and "an answer sent via link-local multicast would not reach a querier outside the local link". — [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762) [P]
- ESPHome "uses mDNS to discover devices and resolve their `.local` names", which breaks on "a network where your server and your devices sit on different subnets or VLANs" and in Docker without host networking. Remedies it documents: "If your router supports Avahi, you can make mDNS work across subnets" (enable it on both subnets and allow UDP to 224.0.0.251 port 5353), or assign a static IP with `manual_ip` and override the connection address with `use_address`; device status then falls back to an ICMP ping sweep. — [ESPHome FAQ](https://esphome.io/guides/faq/) [P]
- Avahi's reflector: with `enable-reflector=yes`, "avahi-daemon will reflect incoming mDNS requests to all local network interfaces"; `reflect-filters=` limits which services are reflected and `allow-interfaces=` limits the interfaces used. Default is off. — [avahi-daemon.conf(5)](https://manpages.debian.org/bookworm/avahi-daemon/avahi-daemon.conf.5.en.html) [P]

**Self-hosted WireGuard when no port can be forwarded upstream**
- WireGuard is silent by default; a peer behind NAT that must receive traffic "must keep the NAT/firewall mapping valid, by periodically sending keepalive packets" — `PersistentKeepalive`, with 25 seconds "a sensible interval". — [WireGuard quick start](https://www.wireguard.com/quickstart/) [P]
- Two NATed peers "don't know what the `ip:port` of their peer is" and need a coordination side channel plus STUN; "hard" (endpoint-dependent) NATs defeat this and a relay is the fallback. Even with IPv6, a stateful firewall requires that "packets must flow out before packets can flow back in". — [Tailscale, How NAT traversal works](https://tailscale.com/blog/how-nat-traversal-works) [P]
- VPS relay pattern (tutorial dated 28 May 2026): a VPS with a public IPv4 runs WireGuard; the home server dials out with `PersistentKeepalive = 25` (called "critical"); phones connect to the VPS, which has IP forwarding enabled and routes between peers. The tutorial describes "two separate VPN tunnels", i.e. the tunnel terminates on the VPS, which decrypts and forwards. — [Hetzner community tutorial](https://community.hetzner.com/tutorials/bypass-cgnat-with-a-wireguard-vps-relay/) [P]
- Tailscale needs no inbound ports in most cases: it uses outbound TCP 443 (coordination server and DERP relays), UDP 41641 for direct WireGuard traffic and UDP 3478 for STUN; if no direct path can be made, traffic goes through DERP relays, which is slower. — [Tailscale, firewall ports](https://tailscale.com/kb/1082/firewall-ports) [P]
- A Tailscale subnet router is a device that advertises LAN routes so other devices "without installing the Tailscale client" become reachable; on Linux it requires IP forwarding (`net.ipv4.ip_forward`, `net.ipv6.conf.all.forwarding`), `tailscale set --advertise-routes=...` and route approval; source NAT is on by default. — [Tailscale, subnet routers](https://tailscale.com/kb/1019/subnets) [P]
- A self-hosted Headscale control server needs a host with a public IP and HTTPS on port 443, so it cannot live inside this home network. — [Headscale requirements](https://headscale.net/stable/setup/requirements/) [P]

### Inferences
- Recommended topology: ISP/building router (treated as untrusted, like the internet) → WAN port of the user-owned router → two zones. A trusted zone (default `lan`: phones, Mac, hub laptop, preferably by Ethernet) and an `iot` zone on its own SSID and subnet whose policy is reject and which has **no** forwarding to `wan`. Add a `lan` → `iot` forwarding so the hub can initiate connections to devices, and narrow rules from `iot` to the router (DHCP, DNS, NTP) and from `iot` to the hub's address on the broker/API ports only. Because forwardings are one-way and the IoT zone has none towards `wan`, IoT devices have no internet path; this follows from the default-config semantics above rather than from an OpenWrt how-to, which could not be read.
- The router must be in routing (NAT) mode; a bridged "dumb access point" would put devices on the ISP router's own LAN and isolate nothing. The inner subnets must differ from the ISP router's LAN range. Both points are standard practice, not sourced here.
- Double NAT is an advantage in a rented or shared building: OpenWrt's default `wan` zone rejects input and drops forwarding, so equipment on the building side cannot initiate connections into the flat's networks.
- With internet blocked, IoT devices lose NTP and vendor update servers: provide time from the router or hub and push firmware from the hub.
- mDNS: phones and the hub share the trusted zone, so the PWA reaches the hub normally. For ESP devices in the IoT zone, the more robust design is for devices to dial a fixed hub address or DNS name handed out by the router (MQTT/WebSocket) and for the hub to use static leases, with an Avahi reflector limited by `reflect-filters` as an optional convenience.
- Remote access here is the CGNAT case of question 5 regardless of the ISP: direct inbound WireGuard only works if the upstream router happens to honour UPnP/NAT-PMP/PCP requests or passes inbound IPv6, neither of which can be relied on. The practical options are (a) Tailscale's free plan with the hub laptop (or router) as subnet router — no port forwarding, no fee, but a third-party control plane; or (b) a rented VPS relay — self-controlled but a monthly fee, and in the simple two-tunnel design the VPS sees decrypted traffic, so keep HTTPS to the hub inside the tunnel or nest an end-to-end WireGuard tunnel through it.
- Running the tunnel endpoint on the laptop keeps the router simple; running it on the router keeps remote access alive when the laptop is down (useful for SSH disk-unlock in question 10).

### Gaps
- openwrt.org blocked automated access, so OpenWrt's wiki pages on cascaded routers/double NAT, guest or IoT Wi-Fi setup, mDNS packages, WireGuard and Tailscale on OpenWrt, and IPv6 without prefix delegation were not read. GL.iNet's documentation site did not resolve, so stock-firmware features (built-in WireGuard/Tailscale, guest network, repeater mode for joining building Wi-Fi) are unverified.
- Whether typical EU ISP routers honour port-mapping requests from a downstream router, or allow inbound IPv6, was not researched; nor was IPv6 handling for the inner network (relay, NAT66) and whether the IoT zone's block needs separate IPv6 attention.
- No model-level buying comparison (price, RAM/flash, Wi-Fi 6/7) was done; Cudy's flash-chip warning means checking the serial number and required OpenWrt version before flashing.
- ESP32 interaction with client isolation and WPA3 modes was not researched.

## 10. (Added) Running a laptop as a 24/7 Linux server

### Takeaway
A laptop works as an always-on hub (its battery is a built-in UPS and it has a console for recovery) provided four things are set deliberately: systemd-logind must ignore the lid switch and all sleep states must be disabled; the battery must be held well below full charge with firmware charge thresholds (vendors suggest about 60% for always-plugged machines, TLP suggests 40–50%); services must be systemd units or containers that restart on failure and start at boot without a login; and disk encryption must be reconciled with unattended reboots, because a LUKS passphrase prompt stops the hub from coming back by itself — the alternatives are TPM2-bound unlock, network-bound unlock (Clevis/Tang), SSH unlock from the initramfs, or encrypting only the data volume.

### Cited Findings

**Lid switch and suspend prevention**
- `logind.conf`: `HandleLidSwitch=` defaults to "suspend"; `HandleLidSwitchExternalPower=` is "completely ignored by default (for backwards compatibility)", so the general setting applies on AC unless it is set explicitly; `HandleLidSwitchDocked=` defaults to "ignore"; "ignore" means logind never handles the event. `LidSwitchIgnoreInhibited=` defaults to "yes", i.e. inhibitor locks do not block the lid action. Drop-ins go in `/etc/systemd/logind.conf.d/`. — [logind.conf(5)](https://www.freedesktop.org/software/systemd/man/latest/logind.conf.html) [P]
- Debian's recipe: set `HandleLidSwitch=ignore` and `HandleLidSwitchDocked=ignore` in `/etc/systemd/logind.conf`, then restart `systemd-logind` or reboot; to disable sleep entirely create `/etc/systemd/sleep.conf.d/nosuspend.conf` with `AllowSuspend=no`, `AllowHibernation=no`, `AllowSuspendThenHibernate=no`, `AllowHybridSleep=no` — "possibly desirable on servers". — [Debian Wiki, Suspend](https://wiki.debian.org/Suspend) [P]; option semantics (since systemd 240) — [systemd-sleep.conf(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd-sleep.conf.html) [P]
- GNOME has its own Automatic Suspend with separate "On Battery Power" and "Plugged In" switches (Settings > Power). — [GNOME Help](https://help.gnome.org/users/gnome-help/stable/power-autosuspend.html.en) [P]

**Battery charge thresholds**
- Kernel interface: `/sys/class/power_supply/<bat>/charge_control_start_threshold` ("a battery percentage level, below which charging will begin"), `charge_control_end_threshold` ("above which charging will stop"; "Drivers will round written values to the nearest supported value"), `charge_behaviour` (`auto`, `inhibit-charge`, `force-discharge`), and a "Long Life" charge type for hardware with a single fixed limit. — [Linux kernel ABI, sysfs-class-power](https://www.kernel.org/doc/Documentation/ABI/testing/sysfs-class-power) [P]
- TLP exposes these as `START_CHARGE_THRESH_BAT0` / `STOP_CHARGE_THRESH_BAT0` (none set by default; both must be given). Support is per vendor: ThinkPad (start 0–99, stop 1–100), Lenovo IdeaPad/ThinkBook (conservation mode with a fixed, model-dependent limit, often 60 or 80), ASUS (stop 1–100, some models only 40/60/80, reset at power-on), Dell (start 50–95, stop 55–100, kernel 6.12+), Huawei, LG (80), Samsung (fixed 80), Sony (50/80), Toshiba/Dynabook (80), MSI (10–100), System76, Tuxedo/Clevo, Apple Silicon (80), Framework/Chromebook (kernel 6.12+ driver). Acer and HP are not listed; unlisted hardware is unsupported. — [TLP battery care](https://linrunner.de/tlp/settings/battery.html) [P]; [TLP vendor specifics](https://linrunner.de/tlp/settings/bc-vendors.html) [P]
- TLP's guidance: for a laptop that is usually plugged in, "maximizing battery lifetime at the cost of a greatly reduced runtime may be acceptable, with values like starting charge at 40% and stopping at 50%"; TLP's sample default is 75/80. Thresholds do not force a discharge. Charging is controlled by firmware, so thresholds stored in the embedded controller work "even when the laptop is switched off or no operating system is running"; removing the battery may reset them. — [TLP battery FAQ](https://linrunner.de/tlp/faq/battery.html) [P]
- Vendor guidance example: ASUS's Maximum Lifespan mode (stop above 60%, resume below 58%) "is recommended when the computer is always powered by AC adapter", because a battery held at 98–100% for long periods has a reduced life. — [ASUS support](https://www.asus.com/support/faq/1032726/) [P]
- GNOME 48 (19 Mar 2025) added "Preserve Battery Health", which limits charge to 80% while plugged in on supported hardware. — [GNOME 48 release notes](https://release.gnome.org/48/) [P]

**Automatic service restart and start at boot**
- `Restart=` defaults to `no`; "Setting this to `on-failure` is the recommended choice for long-running services"; `RestartSec=` defaults to 100 ms; `RestartSteps=`/`RestartMaxDelaySec=` (systemd 254+) give exponential back-off; `WatchdogSec=` restarts a service that stops sending keep-alive pings. — [systemd.service(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) [P]
- Restarts are rate-limited by `StartLimitIntervalSec=`/`StartLimitBurst=`: once exceeded the unit is no longer restarted automatically; `StartLimitIntervalSec=0` disables the limit and `StartLimitAction=` can reboot the machine. `WantedBy=multi-user.target` plus `systemctl enable` starts a unit at boot. — [systemd.unit(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html) [P]
- `loginctl enable-linger` starts a user's service manager at boot and keeps it after logout, so per-user services run with nobody logged in. — [loginctl(1)](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html) [P]
- `RuntimeWatchdogSec=` programs a hardware watchdog to "automatically reboot the system if it is not contacted within the specified timeout interval"; off by default and requires a watchdog device. — [systemd-system.conf(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd-system.conf.html) [P]
- Docker restart policies: `no` (default), `on-failure[:max-retries]`, `always`, `unless-stopped`; a policy applies only after a container has run for at least 10 seconds; Docker recommends restart policies over process managers and warns not to combine the two. — [Docker docs](https://docs.docker.com/engine/containers/start-containers-automatically/) [P]
- Debian unattended-upgrades installs Debian and Debian-Security updates by default; `Unattended-Upgrade::Automatic-Reboot` defaults to "false" and, if enabled, will "Automatically reboot *WITHOUT CONFIRMATION*" when a reboot is required, optionally at `Automatic-Reboot-Time` (example "02:00"). — [unattended-upgrades default config](https://raw.githubusercontent.com/mvo5/unattended-upgrades/master/data/50unattended-upgrades.Debian) [P]; [Debian Wiki](https://wiki.debian.org/UnattendedUpgrades) [P]

**Full-disk encryption versus unattended reboot**
- TPM2-bound unlock: `systemd-cryptenroll --tpm2-device=auto` enrols the TPM into a LUKS2 volume and `tpm2-device=auto` in `/etc/crypttab` unlocks it at boot with no prompt. Volumes are typically bound to PCR 7 (Secure Boot state), plus 11 and 14 where applicable; fixed PCR values are brittle across updates, which signed PCR policies address. `--tpm2-with-pin` makes "the TPM a second factor rather than a single point of failure" (but brings back a prompt), and `--recovery-key` enrols a fallback. The current man page says no PCRs are bound unless the option is given. — [systemd-cryptenroll(1)](https://www.freedesktop.org/software/systemd/man/latest/systemd-cryptenroll.html) [P]
- Network-bound unlock: Clevis is "a pluggable framework for automated decryption" with pins for Tang (a server on the network, no key escrow), TPM2 (optionally PCR-bound) and Shamir secret sharing to combine them (for example require both Tang and TPM2); it integrates with dracut and initramfs-tools and needs networking in the initramfs. — [Clevis README](https://github.com/latchset/clevis) [P]
- SSH unlock: Debian supports unlocking the root volume remotely with `dropbear-initramfs` — an SSH server in the initramfs, keys in `/etc/dropbear-initramfs/authorized_keys` (restrictable to `/bin/cryptroot-unlock`), then `cryptroot-unlock` over SSH. — [Debian cryptsetup README](https://cryptsetup-team.pages.debian.net/cryptsetup/README.Debian.html) [P]

### Inferences
- Disk-encryption options compared (derived from the findings above):

| Option | Reboots unattended? | Protects against | Caveat |
|---|---|---|---|
| LUKS passphrase at the console | no | theft of the powered-off laptop | someone must be present after every reboot or deep power loss |
| TPM2 auto-unlock, no PIN | yes | the disk being removed and read elsewhere; boot-chain tampering if PCR-bound | a thief who takes the whole laptop gets a booted system, so protection rests on login and OS security; PCR policies can break on firmware or kernel updates — keep a recovery key |
| TPM2 plus PIN | no | theft of the whole laptop | prompt at every boot |
| Clevis with a Tang server on the home LAN | yes, while that server is reachable | theft of the laptop alone, since it cannot unlock away from the home network | needs a second always-on device and initramfs networking |
| SSH unlock (dropbear) | only with the owner's action, from anywhere the hub's network is reachable | theft | needs initramfs networking, and remote reachability must not depend on the locked hub itself |
| Unencrypted system, encrypted data volume | system yes, data only after unlock | theft of data | services needing the data wait for the unlock |

- In a rented flat the realistic threats are burglary and third-party access, and the hub stores the private CA key, broker credentials, Wi-Fi keys and voice data, so some encryption is warranted. Network-bound unlock tied to the user-owned router, or TPM2 unlock with its weaker theft protection understood, are the two ways to keep unattended reboots; otherwise accept the passphrase and rely on the laptop's battery to make unplanned reboots rare.
- Enable automatic reboots after updates only if unlock is unattended; otherwise leave `Automatic-Reboot` off and reboot by hand.
- Set the lid behaviour explicitly for the AC case (`HandleLidSwitchExternalPower=ignore`) as well as the general one, and disable sleep at the systemd level so that a desktop environment's idle auto-suspend cannot put the hub to sleep; running without a graphical session avoids the issue altogether.
- A 40–60% charge cap still leaves the battery useful as a short-outage UPS while avoiding the high state of charge that vendors link to wear; brands TLP cannot control (HP, Acer) need a firmware-setup charge limit or the smart-plug approach from question 8.
- Each hub component should be its own system unit with `Restart=on-failure` and a restart delay of a few seconds, with rate-limiting relaxed or back-off enabled so a slow dependency does not leave it permanently stopped; choose either systemd or Docker restart policies per component, not both.
- Wired Ethernet to the user-owned router is preferable for the hub: early-boot unlock methods and server-style reliability both assume it.

### Gaps
- No source was read on thermal effects of running with the lid closed (relevant under sustained AI load), on firmware "power on when AC returns" settings, or on battery swelling in laptops specifically.
- The GNOME login screen's own idle-suspend behaviour and its override could not be verified (ArchWiki blocked; Debian's page is silent).
- Lenovo's and other vendors' own charge-level recommendations were not read; ASUS is the only vendor statement cited.
- The default PCR binding of TPM2 enrolment has differed between systemd versions; check the installed version's man page.
- Whether a given laptop has a usable hardware watchdog, and whether Wi-Fi can be used for initramfs networking, were not researched.
