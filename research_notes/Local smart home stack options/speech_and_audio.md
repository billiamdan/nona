# Local speech and audio stack for an English + Russian smart-home voice assistant (state as of November 2026)

> Research method note (applies to every section): general web search was unavailable for this assignment (the shared search budget was already used up), so everything below comes from direct fetches of primary sources (model cards, repositories, vendor and project documentation) on 2026-11-25. Community experience reports (Reddit, Home Assistant community threads, most Habr comparisons) could not be discovered without search and are listed under Gaps. ## Objective: recommended component per pipeline stage (CPU-only x86 laptop, 16 GB RAM; optional Apple Silicon Mac on the LAN)

### Takeaway
The best-evidenced fully local pipeline is: microWakeWord on the satellite (two wake words to pick the language) -> Silero VAD endpointing -> GigaAM v3 for Russian plus a Parakeet-TDT-v3-family model for English, both through ONNX (onnx-asr / OHF-Voice wyoming-faster-whisper) -> intent matching or LLM -> Piper (ru_RU + en_US voices) as the fast baseline TTS, with Silero v5 as the higher-quality Russian option under a non-commercial licence. A custom Python hub can drive ESPHome voice satellites directly with aioesphomeapi; Home Assistant's own ESPHome satellite code is the open reference implementation.

### Cited Findings
- Wake word on device: Home Assistant Voice Preview Edition ships "Okay Nabu", "Hey Jarvis", "Hey Mycroft" running on the microWakeWord engine; firmware for ESP32 and XMOS chip is fully open source — [Home Assistant Voice PE](https://www.home-assistant.io/voice-pe/)
- One satellite can carry "up to two wake words and voice assistant pipelines" (example: "Okay Nabu" for English, "Hey Jarvis" for French) since Home Assistant 2025.10 — [Voice Chapter 11, 2025-10-22](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)
- Russian STT accuracy leader on independent Russian test sets: GigaAM3 RNNT average WER 7.19 over 11 sets, versus Vosk 0.62 at 9.53 and T-one streaming at 11.62 (post dated 2026-05-24) — [alphacephei, In-depth evaluation of ASR engines](https://alphacephei.com/nsh/2026/05/24/asr-details.html)
- GigaAM v3 CTC runs at 58.8x real time and Parakeet TDT 0.6B v3 at 33-35x real time on a desktop AMD Ryzen 7 9800X3D CPU through ONNX Runtime; Whisper large-v3-turbo only 2.9-5.4x — [onnx-asr benchmarks](https://istupakov.github.io/onnx-asr/benchmarks/)
- The OHF-Voice Wyoming STT server (`wyoming-faster-whisper`) selects a backend per language: faster-whisper, transformers, qwen3-asr, sherpa (Parakeet TDT v3, 25 languages), funasr, and onnx-asr (`ru` via GigaAM) — [wyoming-faster-whisper](https://github.com/rhasspy/wyoming-faster-whisper)
- Piper is "a fast and local neural text-to-speech engine that embeds espeak-ng for phonemization", GPL-3.0, with CLI, HTTP server, Python and C/C++ APIs; four ru_RU voices exist (denis, dmitri, irina, ruslan) — [piper1-gpl](https://github.com/OHF-Voice/piper1-gpl); [piper-voices ru_RU](https://huggingface.co/rhasspy/piper-voices/tree/main/ru/ru_RU)
- Silero TTS v5 Russian models have automatic stress and homograph handling; all Silero models are under CC-NC-BY except the MIT `base` CIS models — [silero-models](https://github.com/snakers4/silero-models)
- aioesphomeapi's `APIClient` exposes `subscribe_voice_assistant`, `send_voice_assistant_event`, `send_voice_assistant_audio`, `send_voice_assistant_timer_event`, `send_voice_assistant_announcement_await_response`, and get/set voice-assistant configuration — [aioesphomeapi client.py](https://raw.githubusercontent.com/esphome/aioesphomeapi/main/aioesphomeapi/client.py)

### Inferences
- Recommended stack (my synthesis of the cited evidence; per-stage evidence is in the sections below):
  - Wake word: microWakeWord on ESP32-S3 satellites, Ava (Android) and linux-voice-assistant (Linux); assign one wake word per language so the hub knows which STT model and TTS voice to use. openWakeWord remains a server-side fallback (its pretrained models are CC BY-NC-SA, acceptable for personal use).
  - VAD / endpointing: Silero VAD (MIT) on the hub; the microWakeWord VAD model on the device.
  - STT: GigaAM v3 (MIT, 220-240M parameters) for Russian and Parakeet TDT 0.6B v3 (CC-BY-4.0) or a 2026 derivative for English, both through onnx-asr (MIT) directly in Python or through wyoming-faster-whisper. Whisper large-v3-turbo is the one-model fallback but is roughly 10x slower on CPU and weaker on Russian commands.
  - TTS: Piper (GPL-3.0) with a ru_RU and an en_US voice as baseline; Silero v5 for Russian when better stress/homographs matter (non-commercial licence); KittenTTS 2 or Supertonic 3 are single-model bilingual candidates that still need a listening test.
  - With the Apple Silicon Mac: move STT to Core ML / MLX (Parakeet v3 at about 190x real time on M4 Pro) and TTS to Qwen3-TTS through mlx-audio or qwentts.cpp; also use the Mac for custom wake-word training.
  - Satellites: Home Assistant Voice PE (EUR 59 MSRP) or a ReSpeaker Lite / XVF3800 board with XIAO ESP32-S3 running ESPHome; spare Android phones with Ava; Linux boxes with linux-voice-assistant; the hub talks to all of them through aioesphomeapi.
  - "People are waking up" detection: publish only sound level from ESP32 nodes (ESPHome `sound_level`), run a small AudioSet tagger (sherpa-onnx Zipformer, YAMNet or EfficientAT) where compute allows and publish labels only, then fuse with presence and alarm signals on the hub.
- 16 GB RAM is not a constraint for this stack: Parakeet v3 needs about 2 GB to load, GigaAM v3 is a 220-240M-parameter model, and Piper/Silero voices are tens of MB, so both STT models can stay loaded.

### Gaps
- No end-to-end measurement of this exact pipeline on a mobile x86 CPU was found; all speed figures are from desktop/server CPUs or vendor cards.
- The intent-matching / LLM stage is out of scope for these notes.

## Speech-to-text for English + Russian, including mixed utterances

### Takeaway
No single open model is clearly best for both languages on CPU: Russian-specialised GigaAM v3 is far more accurate on Russian commands and far-field audio than Whisper or Parakeet, while Parakeet-TDT-v3-family models are the fastest accurate English option and also cover Russian with automatic language detection. None of the candidates is documented as handling Russian/English switching inside one utterance; NVIDIA says Parakeet v3 is "not fully tuned" for it.

### Inferences
- Recommended design: two specialised models rather than one multilingual model. Route by wake word (one wake word per language), or decode every utterance with both GigaAM v3 and Parakeet v3 in parallel and keep the transcript that matches an intent; both models are fast enough on CPU that double decoding of a 3-second command should still take well under a second on a desktop-class CPU (laptop CPUs will be slower by an unknown factor).
- Parakeet v3 alone is risky for Russian commands: its auto language detection is reported to pick the wrong language and it scored 19.5% WER on short Russian commands versus 1.9% for GigaAM2. The 2026 derivatives (parakeet-ultra, fluid-speech-pro) improve FLEURS Russian by about 0.6-0.7 points, which does not close that gap.
- Whisper large-v3-turbo is the only candidate with a single model, broad language coverage and explicit language forcing, but at 3-5x real time on a fast desktop CPU a short command would take roughly one to several seconds on a laptop; the Podlodka fine-tune is the better Whisper choice for Russian far-field audio.
- English device names inside Russian sentences: Russian-only models with a Cyrillic alphabet (T-one states this explicitly) can only emit a Cyrillic approximation, so the hub should hold Cyrillic aliases for English device names; with Whisper-family servers, `--initial-prompt` / name biasing is the documented lever.
- Qwen3-ASR and Voxtral are GPU-oriented (vLLM, 16 GB GPU for Voxtral Realtime); they are candidates for the Mac through MLX rather than for the laptop. The int4 ONNX Qwen3-ASR-0.6B does run on CPU (2.2 s for a 3.2 s command on a Raspberry Pi 5, so plausibly under a second on a laptop), but its Russian WER (FLEURS 9.91) is well behind GigaAM v3.
- A language-ID front end is available off the shelf (VoxLingua107 in transcribe.cpp, spoken language identification in sherpa-onnx) if routing by wake word is not wanted; accuracy on 1-3 second commands is not documented in the sources read.
- Streaming STT on CPU for Russian is available from Vosk small streaming, T-one and Nemotron 3.5 streaming; GigaAM and Parakeet v3 are used offline per utterance, which is acceptable for short commands.

### Gaps
- No measured real-time factor on a laptop-class x86 CPU; onnx-asr figures are for a desktop Ryzen 7 9800X3D, parakeet-redux for an EPYC server CPU.
- No independent Russian benchmark of the 2026 models (parakeet-ultra, parakeet-redux, fluid-speech-pro, Nemotron 3.5 streaming, GigaAM Multilingual) on command-style or far-field data; only vendor FLEURS figures.
- No benchmark of intra-utterance English/Russian code-switching for any model; only the NVIDIA statement and the Podlodka "not evaluated" note.
- Whether GigaAM v3 e2e models emit Latin-script tokens for English words was not confirmed.
- Whisper small/base/medium Russian WER was not retrieved; the Hugging Face Open ASR Leaderboard and Habr comparison articles were not consulted (no search; dynamic page).
- transcribe.cpp publishes no speed table, so there is still no laptop-class figure for GGUF Parakeet or GigaAM.

## Text-to-speech for English and Russian on CPU

### Takeaway
Piper remains the practical CPU baseline (actively developed as piper1-gpl, GPL-3.0, four Russian voices) and Silero v5 is the documented leader for Russian stress and homographs but is non-commercial and has no current English model. Kokoro has no official Russian; 2026 added several small CPU-capable models that cover both languages in one model (KittenTTS 2, Supertonic 3) and Russian-specific tiny models, none of them independently evaluated here.

### Cited Findings
- Piper (piper1-gpl): GPL-3.0; README says the Open Home Foundation "is seeking maintainers"; 6.4k stars, 419 commits; install with `pip install piper-tts` — [piper1-gpl](https://github.com/OHF-Voice/piper1-gpl)
- Piper changelog: v1.3.0 moved development to OHF-Voice, embedded espeak-ng and changed the licence to GPLv3; the unreleased section adds `libpiper` streaming for voices split into encoder and decoder ("first sound arrives in about 0.2 seconds regardless of sentence length"), roughly 3x faster multi-threaded inference, training fixes and licensing docs; it references an event on 2026-11-19, so the project was active in November 2026; no Russian-specific changes — [piper1-gpl CHANGELOG](https://github.com/OHF-Voice/piper1-gpl/blob/main/CHANGELOG.md)

- Shtorm-PocketTTS-RU (v2 dated 2026-10-01): Russian fine-tune of Kyutai Pocket TTS, about 100M parameters, CC-BY-4.0, voice cloning from about 5 seconds, manual stress marks, "Latin script is not supported" — [Shtorm-PocketTTS-RU](https://huggingface.co/ArtShtorm/Shtorm-PocketTTS-RU)

- OmniVoice (k2-fsa, paper 2026-04-01): zero-shot TTS for 600+ languages, 0.6B parameters, model weights CC-BY-NC — [OmniVoice](https://huggingface.co/k2-fsa/OmniVoice)
- Streaming TTS effect: for a long LLM answer, time to first audio fell from more than five seconds to "about half a second" with streaming — [Voice Chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)
- Apple Silicon: mlx-audio lists Kokoro, KittenTTS, Qwen3-TTS, Chatterbox (23 languages), OmniVoice and MOSS-TTS among supported TTS models with a `--stream` option — [mlx-audio](https://github.com/Blaizzy/mlx-audio)

### Inferences
- Baseline recommendation: Piper with one ru_RU and one en_US voice, choosing the voice from the detected language of each response; it is the only option that is simultaneously Wyoming-native, OpenAI-API-servable (Speaches), streaming-capable and trivially real-time on CPU.
- Quality upgrade for Russian: Silero v5 (`v5_6_ru`) for its built-in stress and homograph handling; the CC BY-NC licence permits personal non-commercial use but blocks any later commercial reuse. English would still come from Piper or Kokoro.
- Stress is the main Russian quality risk for every non-Silero option: Piper relies on espeak-ng phonemization, Qwen3-TTS ignores stress marks a third of the time, and the small 2026 models all bolt on RUAccent. Running RUAccent as a text pre-processor is the common pattern.
- Mixed-language sentences: no model card claims intra-sentence Russian/English switching. The workable approaches are transliterating English device names into Cyrillic before synthesis, or a model whose voices are cross-lingual (KittenTTS 2).
- With the Apple Silicon Mac, Qwen3-TTS 0.6B through mlx-audio or qwentts.cpp (Metal) becomes realistic for more natural, streaming speech; on the CPU-only laptop its speed is undocumented.

### Gaps
- No x86 laptop CPU real-time factor for Piper, KittenTTS 2 or Supertonic 3 was found (Silero v5 has a desktop i9 figure only).
- Piper Russian voice quality levels and espeak-ng stress error rates were not confirmed from a source.
- Silero's exact wording on what personal use is allowed beyond the CC BY-NC name was not retrieved, and Silero publishes no stress/homograph accuracy numbers in the pages read.
- KittenTTS 2 licence is stated inconsistently (Apache-2.0 on the Mini model card, "Stellon Labs Community License" for weights in the repository); the licence text was not read.
- TTS arena leaderboards were not consulted; an "Open TTS Leaderboard" is referenced by a model card but was not read.
- The Chatterbox "retired" notice and the Supertonic repository archive date were each seen once and not double-checked.

## Wake word and voice activity detection

### Takeaway
microWakeWord (on-device, ESP32-S3 class, Apache-2.0 models) is the default for ESPHome satellites and now also runs on Android (Ava) and Linux (linux-voice-assistant); openWakeWord is the server-side alternative with an easy Colab trainer but English-only training and non-commercial pretrained models. Custom microWakeWord training is officially "very difficult", and community trainers with web UIs (NVIDIA Docker and Apple Silicon) are the practical route in 2026.

### Cited Findings
- openWakeWord: code Apache-2.0, pretrained models CC BY-NC-SA 4.0; latest release mentioned is v0.6.0 (2024-02-11); a frozen Google speech-embedding backbone plus a small per-word classifier; targets are a false-reject rate below 5% and fewer than 0.5 false accepts per hour; one Raspberry Pi 3 core runs 15-20 models; 80 ms frames; optional Speex noise suppression and Silero VAD gating; "Only English is supported"; custom verifier models can restrict activation to known voices — [openWakeWord](https://github.com/dscripka/openWakeWord)
- openWakeWord custom training: a Colab notebook produces a model in under an hour from synthetic speech; "a minimum of several thousand" generated examples recommended; shipped models used about 30,000 hours of negative data — [openWakeWord](https://github.com/dscripka/openWakeWord)
- Home Assistant's guide: "Currently, only wake words in English are supported"; the Colab run takes 30-60 minutes and uses Piper to generate clips; choose 3-4 syllables and adjust the spelling until the generated pronunciation matches yours — [Home Assistant: create a wake word](https://www.home-assistant.io/voice_control/create_wake_word/)
- microWakeWord: "A TensorFlow based wake word detection training framework using synthetic sample generation suitable for certain microcontrollers", "currently available as an early release", inference every 30 ms; "Training a model that works well is still very difficult" and the basic notebook "will most likely not be usable!"; Apache-2.0 — [OHF-Voice/micro-wake-word](https://github.com/OHF-Voice/micro-wake-word); [kahrendt/microWakeWord](https://github.com/kahrendt/microWakeWord)
- ESPHome `micro_wake_word`: several models can be loaded and enabled/disabled at runtime; an optional VAD model reduces "false accepts from non-speech sounds"; `probability_cutoff` trades false accepts against false rejects; models load by name, GitHub shorthand, URL or local path; the tensor arena uses PSRAM "when available, otherwise in internal RAM"; manifests carry `trained_languages` — [ESPHome micro_wake_word](https://esphome.io/components/micro_wake_word/)
- Official microWakeWord model files are Apache 2.0 for "the entire contents of this repository" — [micro-wake-word-models](https://github.com/esphome/micro-wake-word-models)
- On Voice PE, running three microWakeWord models (VAD, "Okay Nabu", "Stop") while decoding two FLAC streams uses 35% CPU (down from 72%); models can be switched on the fly — [Voice Chapter 10](https://www.home-assistant.io/blog/2025/06/25/voice-chapter-10/)
- Community trainer (NVIDIA GPU, Docker, web UI): trains microWakeWord, openWakeWord and NanoWakeWord models; you enter the phrase and a language, optionally add personal recordings and similar-sounding phrases to reject; outputs an `.esphome.json` for `micro_wake_word`; AGPL-3.0 — [microWakeWord-Trainer-Nvidia-Docker](https://github.com/TaterTotterson/microWakeWord-Trainer-Nvidia-Docker)
- The same trainer exists as a macOS app for Apple Silicon "with full GPU acceleration via Metal (MPS)" — [microWakeWord-Trainer-AppleSilicon](https://github.com/TaterTotterson/microWakeWord-Trainer-AppleSilicon)
- The trainer's README states "Personal samples are optional; reviewed false wakes help reduce unwanted triggers", asks for an NVIDIA GPU with Docker GPU access and `--shm-size=8g`, and defers the language list to `docs/advanced.md` — [trainer README](https://raw.githubusercontent.com/TaterTotterson/microWakeWord-Trainer-Nvidia-Docker/main/README.md)
- NanoWakeWord (Apache 2.0) is a newer training framework with many architectures (DNN, CNN, GRU, CRNN, BcResNet, Conformer and others) that "is language-agnostic" and recommends end-to-end models for non-English wake words; it recommends "at least 10000+ clean data of your wake words" plus negatives of at least three times the positive duration, exports ONNX, and claims a well-trained model "often achieves" less than one false positive every 16-28 hours (vendor claim, undated page) — [NanoWakeWord](https://github.com/arcosoph/nanowakeword)
- `pymicro-wakeword` (Apache-2.0, `pip3 install pymicro-wakeword`) runs microWakeWord models in Python through a pre-compiled TensorFlow Lite library: 16-bit mono 16 kHz audio in 10 ms chunks, built-in `Model.OKAY_NABU`, streaming probability API with a `probability_cutoff` — so a Python hub can run the same wake-word models server-side for satellites that only stream audio — [pymicro-wakeword](https://github.com/OHF-Voice/pymicro-wakeword)
- piper-sample-generator: the default LibriTTS-R generator is "English only", but standard Piper voices in any language can be passed with `--model` (several are cycled); about 100 samples per second on an RTX 2080 Ti; MIT — [piper-sample-generator](https://github.com/rhasspy/piper-sample-generator)
- Silero VAD: MIT, about 2 MB, a 30+ ms chunk is processed in under 1 ms on one CPU thread, 8 and 16 kHz, trained on corpora covering over 6000 languages, ONNX available (undated page) — [Silero VAD](https://github.com/snakers4/silero-vad)
- TEN VAD: "Apache 2.0 with additional conditions"; vendor claims better precision than Silero and WebRTC VAD and says Silero "suffers from a delay of several hundred milliseconds" at speech-to-silence transitions; 10/16 ms hops; ONNX model released June 2025 — [TEN VAD](https://github.com/TEN-framework/ten-vad)
- Server-side endpointing with Silero VAD is built into the Wyoming STT server (`--vad-endpointing`) — [wyoming-faster-whisper CHANGELOG](https://github.com/OHF-Voice/wyoming-faster-whisper/blob/main/CHANGELOG.md)

### Inferences
- A custom name shared by English- and Russian-speaking users is plausible but unproven: stock trainers synthesize English-accented samples, so generate part of the positives with Russian Piper voices (`--model`), add each household member's own recordings in the community trainer, and pick a 3-4 syllable name pronounced the same way in both languages.
- Start with a stock wake word ("Okay Nabu", "Hey Jarvis") to validate hardware and thresholds, then train a custom one on the Apple Silicon Mac.
- Using two wake words to select the language pipeline doubles as the answer to language detection for STT.

### Gaps
- No quantitative false-accept / false-reject data for microWakeWord and no user experience reports were retrieved (no search).
- The community trainers' supported languages (in `docs/advanced.md`), sample counts, training times and quality-report metrics were not retrieved; `pyopen-wakeword` was not read; how custom models are loaded in `pymicro-wakeword` is not documented on its page.
- No evidence on how well an English-trained wake word works for Russian-accented speakers.

## Protocols and satellite software

### Takeaway
The ESPHome native API is now the primary satellite protocol (Wyoming satellite was archived in January 2026), and a custom Python hub can be the server side: aioesphomeapi exposes every voice call and Home Assistant's own satellite module shows the exact event sequence. Android (Ava) and Linux (linux-voice-assistant) satellites emulate an ESPHome device, so one hub-side implementation covers ESP32, Android and Linux.

### Cited Findings
- Wyoming is "A peer-to-peer TCP protocol for voice assistants (basically JSONL + PCM audio)" with events for audio, STT (including `transcript-chunk` streaming), TTS (including `synthesize-chunk` streaming), wake word, VAD, intents, satellites and timers; it "has no authentication or encryption, by design"; MIT — [Wyoming](https://github.com/OHF-Voice/wyoming)
- wyoming-satellite was archived on 2026-01-27: "This project is no longer maintained as it has been replaced by Linux Voice Assistant that uses the ESPHome protocol, which supports the newest features (e.g, media player, stop wake word, start/continue conversation, and timers)" — [wyoming-satellite](https://github.com/rhasspy/wyoming-satellite)
- linux-voice-assistant: "experimental voice satellite software for Home Assistant", speaks the ESPHome protocol via aioesphomeapi on port 6053 with optional API-key encryption; on-device openWakeWord and microWakeWord; announcements, start/continue conversation, timers, mpv media playback, a peripheral WebSocket API; needs 16 kHz mono audio through PulseAudio/PipeWire; amd64, aarch64 and armv7; Apache-2.0 — [linux-voice-assistant](https://github.com/OHF-Voice/linux-voice-assistant)
- linux-voice-assistant latest releases: v1.1.18 (29 Oct), v1.1.17 (28 Oct), v1.1.16 (24 Oct) — [linux-voice-assistant releases](https://github.com/OHF-Voice/linux-voice-assistant/releases)
- ESPHome `voice_assistant`: "Voice Assistant requires Home Assistant 2023.5 or later"; a second microphone channel requires 2026.6.0; audio is 16 kHz, 16-bit, mono; exposes triggers for every pipeline stage and for timers — [ESPHome voice_assistant](https://esphome.io/components/voice_assistant/)
- aioesphomeapi `APIClient.subscribe_voice_assistant(handle_start, handle_stop, handle_audio, handle_announcement_finished, wake_word_audio)` delivers pipeline start/stop and audio; `handle_audio` enables audio over the API connection, otherwise `handle_start` returns a port for server-side audio; `send_voice_assistant_event` and `send_voice_assistant_audio` return pipeline events and TTS audio; external wake words are passed in `get_voice_assistant_configuration` — [aioesphomeapi client.py](https://raw.githubusercontent.com/esphome/aioesphomeapi/main/aioesphomeapi/client.py)
- Home Assistant's ESPHome satellite module uses exactly those calls: API audio when the device advertises `API_AUDIO`, otherwise a UDP server; TTS goes back as paced WAV chunks for speaker devices or as a URL in `TTS_END` for media-player devices; event order is RUN_START, WAKE_WORD_START/END, STT_START, STT_VAD_START/END, STT_END, INTENT_START/PROGRESS/END, TTS_START/END, RUN_END with TTS_STREAM_START/END around audio — [Home Assistant esphome/assist_satellite.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/esphome/assist_satellite.py)
- Ava: "Experimental Android voice assistant for Home Assistant that uses the ESPHome protocol"; Android 8+; up to two on-device microWakeWord models, custom wake words, announcements, media player, timers; unauthenticated port 6053; "intended for static devices"; Apache-2.0; latest release v0.6.2 (15 Jun) — [Ava](https://github.com/brownard/Ava); [Ava releases](https://github.com/brownard/Ava/releases)
- The Home Assistant Android companion app has a wake-word feature: release 2026.11.2 (8 Nov, pre-release) lists "Try to improve wake word use case on slow device" and "Warm up a new wake word engine with background noise" — [Home Assistant Android releases](https://github.com/home-assistant/android/releases)
- Tater is "A fully local, self-hosted replacement for Siri and Alexa" in Python (AGPL-3.0) with its own firmware for Voice PE, Satellite1, ReSpeaker XVF3800 and ESP32-S3-BOX-3 plus a Linux satellite — a non-Home-Assistant hub with voice satellites, though its page does not say whether it uses the ESPHome API — [Tater](https://github.com/TaterTotterson/Tater)
- xiaozhi-esp32 (MIT) is an alternative non-ESPHome firmware: WebSocket or MQTT+UDP transport, ESP-SR offline wake word, boards including M5Stack CoreS3, M5Stack AtomS3R + Echo Base, ESP32-S3-BOX-3 and Waveshare boards, with self-hostable Python, Java and Go servers — [xiaozhi-esp32](https://github.com/78/xiaozhi-esp32)
- Willow (Apache-2.0) with its self-hosted Willow Inference Server is another non-Home-Assistant voice stack; its page gives no maintenance status — [Willow](https://github.com/HeyWillow/willow)

### Inferences
- Yes: a non-Home-Assistant hub can serve ESPHome voice satellites. The hub connects to each satellite as an API client, subscribes to voice-assistant events, runs its own VAD/STT/intent/TTS, and replies with events and audio; the ESPHome documentation's "requires Home Assistant" reflects that Home Assistant is the only official server, not a protocol restriction.
- Because Ava and linux-voice-assistant present themselves as ESPHome devices, the same hub code should serve spare Android phones and Linux boxes without extra protocol work.
- The Home Assistant companion app's wake word is tied to Home Assistant's Assist and is not useful for a custom hub.

### Gaps
- No standalone open-source example of a non-Home-Assistant aioesphomeapi voice server was found (search unavailable; GitHub topic and organisation listing pages timed out); Home Assistant's module is the only verified reference. Whether Tater's hub uses the ESPHome API or only its own firmware protocol is unconfirmed.
- iPhone/iPad options were not researched; no source was retrieved (the companion-app documentation navigation could not be read).
- Wyoming-based Android satellite apps and the companion app's wake-word documentation were not retrieved.

## Satellite hardware in the EU and prices

### Takeaway
Home Assistant Voice Preview Edition (EUR 59 MSRP including tax, XMOS audio front end, open firmware, sold by many EU retailers) is the reference satellite; the cheapest XMOS-based option is the ReSpeaker Lite kit with XIAO ESP32-S3 (USD 29.90 list, 2 mics, about 3 m), and ReSpeaker XVF3800 is the strongest far-field option on paper (4 mics, beamforming, about 5 m, USD 54.90 list for the USB board). ## End-to-end latency budget

### Takeaway
With on-device wake word, per-utterance ONNX STT and streaming TTS, compute is no longer the bottleneck on a CPU-only machine: STT for a short command and time-to-first-audio are each in the low hundreds of milliseconds on desktop-class CPUs, and the end-of-speech silence window dominates. No end-to-end measurement on a laptop CPU was found.

### Cited Findings
- Home Assistant reference timings: Whisper "takes around 8 seconds" per command on a Raspberry Pi 4 and "under a second" on an Intel NUC; Speech-to-Phrase is under one second on a Raspberry Pi 4; Piper generates 1.6 s of audio per second on a Raspberry Pi — [Home Assistant local assistant docs](https://www.home-assistant.io/voice_control/voice_remote_local_assistant/)
- Streaming TTS cut time-to-first-audio for a long LLM answer from more than five seconds to "about half a second" ("A 10x improvement in latency!") — [Voice Chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)
- STT throughput on a desktop CPU (Ryzen 7 9800X3D): GigaAM v3 CTC 58.8x, Parakeet TDT v3 33-35x, Whisper large-v3-turbo 2.9-5.4x real time — [onnx-asr benchmarks](https://istupakov.github.io/onnx-asr/benchmarks/)
- A ternary Parakeet v3 reaches 113x real time on eight x86 server cores and 38x on an Apple M2 CPU — [moondream/parakeet-redux](https://huggingface.co/moondream/parakeet-redux)
- Parakeet TDT v3 on Core ML: about 190x real time on M4 Pro — [FluidAudio](https://github.com/FluidInference/FluidAudio)
- Piper's upcoming streaming mode produces first sound in about 0.2 seconds regardless of sentence length — [piper1-gpl CHANGELOG](https://github.com/OHF-Voice/piper1-gpl/blob/main/CHANGELOG.md)
- Silero VAD processes a 30+ ms chunk in under 1 ms on one CPU thread — [Silero VAD](https://github.com/snakers4/silero-vad)
- Silero TTS v5 generates 37-42 seconds of audio per second on one thread of an Intel i9-10940X and 100-110 on four threads — [Habr: Silero TTS v5 Russian](https://habr.com/ru/articles/961930/)
- Low-end CPU reference for an LLM-style STT model: int4 ONNX Qwen3-ASR-0.6B needs 2.20 s for a 3.2-second command on a Raspberry Pi 5 (4 threads) — [rhasspy/qwen3-asr-0.6b-onnx-int4-merged](https://huggingface.co/rhasspy/qwen3-asr-0.6b-onnx-int4-merged)
- Streaming STT latency settings: Voxtral Realtime recommends a 480 ms delay; Nemotron 3.5 streaming offers 80 ms to 1.12 s chunks — [Voxtral Realtime](https://huggingface.co/mistralai/Voxtral-Mini-4B-Realtime-2602); [Nemotron 3.5 ASR streaming](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b)
- GPU-side reference points: Qwen3-ASR-0.6B time-to-first-token 92 ms; Qwen3-TTS first audio packet as low as 97 ms — [Qwen3-ASR report](https://arxiv.org/html/2601.21337); [Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS)
- Latency levers present in current tooling: server-side VAD endpointing and streaming Qwen3-ASR in the Wyoming STT server; a "Finished speaking detection" setting on ESPHome satellites; paced streaming of TTS audio to the device — [wyoming-faster-whisper CHANGELOG](https://github.com/OHF-Voice/wyoming-faster-whisper/blob/main/CHANGELOG.md); [Home Assistant ATOM Echo tutorial](https://www.home-assistant.io/voice_control/thirteen-usd-voice-remote/); [Home Assistant esphome/assist_satellite.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/esphome/assist_satellite.py)

### Inferences
- Rough budget for a 3-second command on the laptop (estimate, not measured): wake word on device about 0 s extra; end-of-speech silence window 0.3-1.0 s; STT 0.1-0.6 s assuming 5-30x real time on a mobile CPU; intent matching milliseconds; Piper first audio 0.2-0.5 s. Total about 1-2 s after the user stops speaking; an LLM in the loop adds its own time-to-first-token.
- Techniques that matter most, in order: on-device wake word, a short adaptive silence window, keeping models loaded (pre-warmed), a non-autoregressive or transducer STT model instead of Whisper, sentence-level streaming TTS, and skipping spoken confirmations for simple commands.
- The Apple Silicon Mac mainly helps when Whisper-class or LLM-based models are wanted; for GigaAM/Parakeet plus Piper the laptop already has headroom.

### Gaps
- No per-stage measured timings for a CPU-only x86 laptop or for an Apple Silicon end-to-end pipeline were found (community reports not searchable).
- Home Assistant's actual silence-window values for its "finished speaking" settings were not retrieved.

## Speaker identification

### Takeaway
Small local speaker-embedding models are readily available through sherpa-onnx, and openWakeWord offers speaker-specific verifier models, but no source retrieved here quantifies accuracy on short far-field commands; treat speaker identification as a best-effort personalisation signal, not as authentication.

### Cited Findings
- sherpa-onnx lists speaker identification, speaker verification and speaker diarization among its supported functions, with Android, iOS, Linux and macOS support — [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)
- sherpa-onnx speaker-identification docs point to pretrained embedding models on its releases page, Android APKs per model, and Python examples — [sherpa-onnx speaker identification](https://k2-fsa.github.io/sherpa/onnx/speaker-identification/index.html)
- openWakeWord supports custom verifier models: speaker-specific second-stage filters that "can greatly reduce false activations" but make the system less responsive to new voices — [openWakeWord](https://github.com/dscripka/openWakeWord)
- FluidAudio provides offline and streaming speaker diarization on Apple devices — [FluidAudio](https://github.com/FluidInference/FluidAudio)
- Home Assistant's Voice Chapter 11 (October 2025) does not mention speaker identification — [Voice Chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)

### Inferences
- Practical design: enrol each household member with several utterances, compute an embedding for the wake word plus command audio, and compare by cosine similarity with a conservative threshold; fall back to "unknown speaker".
- Short commands (1-3 s), far-field reverberation and children's voices will reduce accuracy; combining with room presence is safer than relying on voice alone.

### Gaps
- Model names, sizes and equal-error rates (WeSpeaker, 3D-Speaker CAM++/ERes2Net, TitaNet, ECAPA-TDNN) were not retrieved.
- No evidence on Russian/English cross-language robustness of speaker embeddings, and no community reports of speaker identification in home voice assistants.

## Household sound-event detection ("people are waking up")

### Takeaway
Small AudioSet-trained taggers are cheap enough to run continuously on a CPU (a 26 MB int8 model runs at about 3% of real time on one thread; YAMNet has 3.7M weights), so the privacy-preserving pattern is to classify on the node or hub and publish only labels or sound levels: ESPHome's `sound_level` sensor already reduces a microphone to dB values on the ESP32. Research here was partial: larger taggers, TinyML on ESP32-S3 and community wake-up-detection practice were not covered.

### Cited Findings
- YAMNet "is a pretrained deep net that predicts 521 audio event classes", a MobileNet v1 design with about 3.7M weights and roughly 69.2M multiplies per 960 ms frame; input 16 kHz mono in 0.96 s frames with 50% overlap; also outputs a 1024-dimensional embedding; balanced mAP 0.306 and d-prime 2.318 on the AudioSet eval set (undated page) — [YAMNet README](https://github.com/tensorflow/models/blob/master/research/audioset/yamnet/README.md)
- EfficientAT (MIT) provides "efficient CNNs for Audio Tagging" distilled from Transformers: mn04_as 0.98M parameters / 0.11B MACs / mAP 43.2; mn10_as 4.88M / 0.54B / 47.1; dymn04_as 1.97M / 0.12B / 45.0; dymn10_as 10.57M / 0.58B / 47.7; dymn20_as 40.02M / 2.2B / 49.1; mn40_as 68.43M / 8.03B / 48.4; the authors note Transformers (PaSST, AST, HTS-AT, BEATs) reach the highest single-model mAP but "scale quadratically with respect to the sequence length"; models also serve as embedding extractors (undated page) — [EfficientAT](https://github.com/fschmid56/EfficientAT)
- sherpa-onnx ships an AudioSet-trained audio tagger, `sherpa-onnx-zipformer-small-audio-tagging-2024-04-15`: int8 model 26 MB (fp32 88 MB); with one thread the examples show real-time factors of 0.027-0.031; output is a ranked list such as `AudioEvent(name="Cat", index=81, prob=0.938876)` — [sherpa-onnx audio tagging models](https://k2-fsa.github.io/sherpa/onnx/audio-tagging/pretrained_models.html)
- Frigate "provides a builtin audio detector which runs on the CPU" because "audio detection is a relatively lightweight operation"; it detects over 500 sound types, enables `bark`, `fire_alarm`, `speech` and `yell` by default, and only runs the classifier when the RMS level exceeds `min_volume`; optional fully local transcription uses sherpa-onnx or faster-whisper and publishes to an MQTT topic — [Frigate audio detectors](https://docs.frigate.video/configuration/audio_detectors/)
- ESPHome `sound_level` measures a microphone's average and peak sound pressure over a configurable window (50 ms to 60 s, default 1000 ms) and reports "relative `dB`, where `0 dB` represents the loudest sound the microphone can measure"; a passive mode measures only while another component is already capturing audio — [ESPHome sound_level](https://esphome.io/components/sensor/sound_level/)
- ESPHome's microWakeWord component can run a small VAD model on the ESP32 to separate speech from non-speech locally — [ESPHome micro_wake_word](https://esphome.io/components/micro_wake_word/)
- sherpa-onnx bundles audio tagging with VAD and keyword spotting in one Apache-2.0 runtime for Linux, Android and iOS — [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)
- The Sleep as Android app emits real-time events over MQTT, webhooks, Tasker or an Intent API, including `sleep_tracking_started/stopped`, `awake` / `not_awake`, `light_sleep` / `deep_sleep` / `rem`, `smart_period`, `alarm_alert_start`, `alarm_snooze_clicked`, `alarm_alert_dismiss`, and (with Sound Recognition active) `sound_event_snore`, `sound_event_talk`, `sound_event_cough`, `sound_event_baby`, `sound_event_laugh`; MQTT is described as publishing "real-time events to your local smart home broker" — [Sleep as Android automation docs](https://sleep.urbandroid.org/docs/services/automation.html)
- ASR models differ strongly in hallucinating text on noise, and Vosk 0.62 adds music/noise detection — relevant if speech presence is inferred from an STT engine — [alphacephei, ASR details 2026](https://alphacephei.com/nsh/2026/05/24/asr-details.html)

### Inferences
- Suggested tiered design (my synthesis): (1) every microphone node publishes only sound level (ESPHome `sound_level`) and, where a voice satellite already runs it, on-device speech/non-speech from the microWakeWord VAD; (2) nodes with more compute (Linux satellite, spare Android phone, the hub itself for satellites that stream) run a small tagger such as the sherpa-onnx Zipformer, YAMNet or EfficientAT mn04/mn10 and publish only class probabilities over MQTT, never storing audio; (3) the hub fuses these with radar presence, bed/sleep sensors and alarm events into a "waking up" state.
- A loudness gate before classification (as Frigate does with `min_volume`) keeps CPU use negligible at night.
- A spare Android phone on a bedside table running Sleep as Android would give alarm-dismissed and awake events over local MQTT without any custom model; the app is not open source as far as I know (not verified here), so it fits "local and subscription-free" only if its free tier suffices.
- AudioSet-trained taggers should cover the target events (speech, alarm clock, footsteps, rustling, coughing are AudioSet classes as far as I recall; the class list was not re-checked), but far-field accuracy for quiet events such as footsteps and rustling is unverified.

### Gaps
- PANNs, AST, BEATs, CLAP zero-shot, CED and any newer 2025-2026 audio taggers were not read; no mAP or CPU-cost figures for them beyond the EfficientAT remark.
- TinyML on ESP32-S3 (ESP-DL, TensorFlow Lite Micro, Edge Impulse) for non-speech events was not researched.
- No source was found on embedding-only node designs or on how reversible audio embeddings are.
- No community reports were retrieved on combining sound with mmWave presence or sleep sensors for wake-up detection (search unavailable); Sleep as Android's MQTT configuration details and licence terms were not read.
- The YAMNet README states no licence, and ESPHome's `sound_level` page does not state whether raw audio can leave the device (it only describes dB outputs).
